# AI 交接包：NoteBase 软件实现

> **这份文件是什么**
> 把已完成的设计方案交给另一个 AI，让它在动手前先做两件事：判断实施路径是否可行，把工作切成四份可以各自跑通的部分。
>
> **怎么用**
> 整份文件贴给它，或让它先读本文件、再读 §2 列出的三份原始材料。§9 是一段可直接复制的开场提示词。
>
> **这份文件不替它做决定的部分**
> 技术栈的最终选型（§7.1 只给判断依据，不给结论）、工期、以及每份内部的实现细节。

---

## 1. 要实现什么

一句话：**一个本地优先的 Markdown 笔记与知识管理桌面工具**。笔记是磁盘上的 `.md` 纯文本文件，**文件是唯一权威数据源**，应用只是这些文件的编辑器和索引器。任何外部工具都能直接读写这些文件。

**在范围内**（按模块）：

| 模块 | 能力 |
|---|---|
| 编辑与存储 | 新建/读取/保存/删除/恢复/重命名、Markdown 编辑与预览、自动保存、崩溃恢复、路径合法性、外部修改检测、回收站 |
| 组织与元数据 | 标签、文件树、frontmatter 属性面板、模板 |
| 检索 | 全文检索、增量索引、过滤排序、**中文子串与两字查询召回** |
| 链接与引用 | `[[双链]]`、反向链接、重命名联动、关系图谱 |
| 导入导出 | 单篇导出 MD/HTML/PDF、整库导出、直接打开已有库 |
| 备份与版本 | 定时备份、备份恢复、单篇版本历史、手动快照 |
| 同步（弹性区） | WebDAV 三方比对、冲突保留双份、离线补传 |
| 设置 | 主题、编辑器偏好、快捷键映射、数据目录迁移、全局唤出 |

**明确不做**：移动端、多人协作、自建云与账号体系、插件系统、CRDT 字符级合并、端到端加密、OCR/手写/语音、Web 版、任务管理、LaTeX、脚注语法。

## 4. 已确认的事实（可直接引用，**不要重新发明**）

### 4.1 性能实测（10 万篇 / 514.5 MB 中文语料）

| 结论 | 数据 |
|---|---|
| 无索引全量扫描 | **8.0–10.2 秒**，P50 均值 8950 ms；**耗时与命中数无关**（命中 1 篇也要 8 秒，零结果查询也要 7990 ms） |
| trigram 索引（≥3 字查询） | 召回 **100%**；完整计数 **1.9–6.1 ms**；首屏 P95 **0.1–0.9 ms**；跨词边界子串同样 100% |
| trigram 索引（<3 字查询） | **静默返回 0 条**（不报错），两字词全部漏 |
| LIKE 回退（两字查询） | 召回 **100%**，耗时 **670–742 ms** |
| unicode61 分词器 | 四字词召回仅 **4.5%–4.6%**，跨词边界与两字词 **0%** → **已否决** |
| 索引体积 | trigram **1276.7 MB = 语料 2.48 倍**（约 515 MB 正文副本 + 762 MB 倒排结构）；unicode61 为 1.19 倍 |
| 全量建库 | trigram **28.3 分钟**；unicode61 41.3 秒 |
| 打开索引 + 首次查询 | 645 ms（trigram）/ 627 ms（unicode61） |
| 单篇增量更新 | P50 **431 ms**，P95 **453 ms**；首轮有 1 次 **10.6 秒尖峰**，复测 100 次未复现 |

**环境**：i5-13420H / 23.7 GB / SSD / Windows 10.0.26200 / ripgrep 14.1.1 / SQLite FTS5。

### 4.2 已核实的第三方能力

| 能力 | 结论 |
|---|---|
| comrak | 100% CommonMark 兼容的 GFM 解析器；表格、任务列表、删除线、自动链接、tagfilter **5 项扩展可独立开关**；**必须显式关闭**脚注、定义列表、上标（设计附录 A 明确不在子集内） |
| WebView2 `PrintToPdfAsync` | 存在；**同一时刻只允许一个打印任务**；目标须为绝对路径且会覆盖同名文件 |
| CommonMark | 当前版本 **0.31.2（2024-01-28）**；核心规范不含表格/任务列表/删除线/脚注 |
| 文件系统事件 | `ReadDirectoryChangesW` 在网络重定向器不支持时返回 `ERROR_INVALID_FUNCTION`；网络目录监控缓冲区上限 64 KB，**溢出会丢弃全部变更** |

## 5. 已定的设计决策（要改必须书面提出）

| 决策 | 结论 | 改了会连带影响 |
|---|---|---|
| D-01 | 桌面运行时选 Tauri（内存与冷启动敏感） | NFR-PER-02/05 的指标、部署视图、打包方式 |
| D-02 | **笔记身份 = 库相对路径**（不是 UUID） | 重命名变成重量级操作 → `rename_journal`、`planOnly` 预演、`E_PARTIAL_RENAME` |
| D-03 | trigram 主索引 + 短查询双阶段扫描 | FR-SRC-05 的三项条件、`E_QUERY_UNSUPPORTED`、20 万篇降级档 |
| D-04 | 索引是**派生缓存**，可删可重建 | 所有查询必须容忍索引缺失（降级为扫描） |
| D-05 | 索引放**应用数据目录**，不放库内 | `vault_id` 机制、库迁移需重建、同步排除规则 |
| D-06 | 编辑器内核选 CodeMirror 6 | 1 MB 文档性能、`![[...]]` 原文保留能力 |
| D-07 | **单一解析器**（comrak），预览/导出/索引共用 | 预览走一次 IPC（150 ms 防抖） |
| D-08 | 同步 = 文件级三方比对（base_hash） | `sync_state`、`sync_tombstone`、冲突副本命名 |
| D-09 | 冲突**保留双份**，不自动合并 | 用户手动合并流程、`conflict.detected` 事件 |
| D-10 | PDF 用平台 WebView 打印 | 分平台差异、`E_PDF_UNSUPPORTED` 降级到 HTML |
| D-11 | 索引一致性 = 事件驱动 + 300 s 对账 | `watcher` 的轮询降级路径 |
| D-12 | 索引存 SQLite | 单写者线程模型、WAL、批提交 |

**如果技术栈必须改（例如环境装不了 Rust）**：D-01 是唯一可动的，但要同时重估 NFR-PER-02（冷启动 ≤2 s）与 NFR-PER-05（内存 ≤1 GB）能否达标，并写一份偏离说明——记录「改了什么、为什么、影响哪几条需求」。其余 11 条决策**与语言无关**，改栈不该动它们。

## 7. 四份怎么切

### 7.1 切的唯一原则

**按「能独立跑通并演示的能力」切，不按文档章节切。**

设计文档按设计要素分章（架构/接口/数据/流程…），那是给评审看的组织方式。实现如果照那个切，每一份都只有半截：接口那份无法验证、数据那份无法运行、流程那份依赖前两份。四份必须各自能以「一次可执行的验证」收尾。

### 7.2 四份工作包

| 工作包 | 内容 | 完成定义（DoD） | 依赖 |
|---|---|---|---|
| **W1 基座** | 工程骨架（IPC/命令总线或 HTTP 入口）、`fs-store`（原子写、路径校验、编码、换行）、`index-store`（10 张表 + FTS5 trigram）、`domain`（路径规则、链接解析） | 命令行/脚本能完成：打开一个 10 万篇库 → 建索引 → 长查询返回正确结果且 P95 ≤50 ms；两字查询走回退路径且**条数等于真值** | 无 |
| **W2 编辑与链接** | `note-svc`（保存判定表、草稿、崩溃恢复）、`link-svc`（`[[...]]` 解析、消歧、反向链接、重命名联动）、`index-worker` 增量写入 | 三个可演示场景：①改文字 2 秒内落盘且崩溃后能恢复；②点 `[[X]]` 跳转、反向链接正确；③重命名后所有引用自动更新，中途取消则零写入 | W1 |
| **W3 检索与导出** | `search-svc` 双路径路由 + 过滤排序、`export-svc`（MD/HTML/PDF + `warnings[]`）、`backup-svc`（备份/校验/恢复 + 恢复前快照）、版本历史 | ①带标签+时间+附件的组合过滤结果正确；②导出含未解析/歧义链接时报 `warnings[]` 而不是静默丢弃；③备份包能在没有本应用的机器上解压还原 | W1 |
| **W4 界面与收口** | `ui` 全量（文件树/编辑器/检索面板/反向链接/设置）、`app-shell`（窗口、全局快捷键、keymap）、`watcher` 对账、`logger`、性能验收、打包 | ①四类角色预设可切换；②空结果/降级/不可服务三种状态视觉可区分；③NFR-PER 全套指标复测通过；④产出可安装的包 | W1–W3 |

**W2 与 W3 可并行**：两者都只依赖 W1 的端口，互不调用。W4 必须最后做，因为它要接全部三份的接口。

**弹性区**：同步（`sync-svc` + `webdav-sync`，F-08）是设计里明确标注的「范围弹性区」，整块可延后到 W4 之后甚至不做。如果做，也只进 W4，不进 W1–W3 的关键路径。

### 7.3 四份之间的交接接口

| 由谁交出 | 交出什么 | 谁接收 |
|---|---|---|
| W1 | `NoteStore` / `IndexStore` 两个端口的**实现 + 契约测试**；建库脚本；10 万篇语料生成脚本 | W2、W3、W4 |
| W2 | `NoteService` / `LinkService`；保存判定表的实现；草稿文件格式 | W3（导出要读链接分类）、W4 |
| W3 | `SearchService` / `ExportService` / `BackupService`；`warnings[]` 与 `missingAssets[]` 的字段约定 | W4 |
| W4 | UI 与打包产物；最终验收报告（VT 结果 + NFR 实测） | — |

### 7.4 合并检查清单（八项，逐条可执行）

1. 组件名、命令名、事件名、错误码、表名与 §3 完全一致，**无新增无改名**。
2. 每个 `CMD-*` 都能在运行中被触发一次，且失败路径返回 §3.4 里的某个错误码。
3. 每条错误码至少被触发过一次（`E_CANCELLED`、`E_INTERNAL` 可豁免）。
4. `notes` 与 `note_fts` 的写入在同一事务内；删除 `index.db` 后能自动重建。
5. 11 个流程各自能跑通正常路径；`F-03`、`F-06`、`F-07`、`F-10` 的异常路径各注入一次。
6. 两字中文查询的**返回条数等于 ripgrep 真值**（不是「非空」即可）。
7. NFR-PER 实测复跑一次：长查询 P95 ≤50 ms、短查询 ≤1 s、索引 ≤3× 语料、重建 ≤30 min。
8. 同一件事在代码注释、文档、错误消息里只有一个说法（红线 #1）。

## 8. 开工前必须由 AI 回答的三个问题

在写第一行代码之前，让它先回答下面三条。答不上来说明它没读懂：

1. **为什么两字中文查询不能直接丢给 trigram 索引？**（期望答案：三元组需要至少 3 个字符，短于 3 会静默返回 0，是正确性缺陷不是性能问题）
2. **为什么索引不能放进库目录？**（期望答案：1.28 GB 含 WAL 文件，会被同步与备份带上，`.db-wal` 在多端同步时必然冲突；且索引是派生缓存，可重建）
3. **重命名一篇被 5 处引用的笔记，失败在第三个文件时怎么恢复？**（期望答案：`rename_journal` 记录已改/未改清单，续跑幂等，已改文件不重复改写；对外返回 `E_PARTIAL_RENAME`）
