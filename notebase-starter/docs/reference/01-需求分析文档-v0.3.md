## 图例与约定

### 优先级判据

优先级必须能追溯到下列三条判据之一。**每条需求的「依据」列标注其判据编号**，不再使用自定义标签。

| 级别 | 判据 |
|---|---|
| 高 | ① 核心链路：每次使用该产品都会触发，缺失则产品不可用 |
| 中 | ② 高频但可用替代手段绕行；或 ③ 影响特定用户群的核心工作流；或 ④ 触发频率低，但缺失会导致不可逆数据损失或数据一致性破坏，且无替代手段 |
| 低 | ⑤ 低频且缺失不影响数据安全，可用替代手段绕行 |

**非功能需求如何使用这套判据**：①~⑤ 借用自功能层，在非功能需求上按**影响面**理解，而非按「功能链路」理解——① 表示该指标不达标会使核心链路不可用（如检索首屏延迟、崩溃丢数据）；②~④ 表示影响特定场景，或存在可接受的降级路径（如索引全量重建慢，可通过后台执行规避）；⑤ 表示可延后且不影响可用性。**这是同一套「影响面 × 发生频率」判据在两类需求上的迁移使用，不是错位。**

### 来源与核实状态

「来源」说明需求从何而来，「核实状态」说明该来源是否已被确认。**二者必须分开**，否则会出现「来源可定位」被误读为「需求已验证」的问题。

| 来源标签 | 含义 |
|---|---|
| `外部规范` | 有公开规范或官方文档可引，已核对原文 |
| `选题描述` | 来自课程提供的选题初步描述（教师给定） |
| `竞品文档` | 来自同类工具的官方文档 |
| `实测` | 来自本次基准实测（附录 B） |
| `人种志-待补` | 计划由作者自身使用记录得出，尚未完成 |
| `访谈-待补` | 计划由目标用户访谈得出，尚未完成 |
| `假设` | 无证据支撑，需核实或推翻 |

| 核实状态 | 含义 |
|---|---|
| `已核实（外部规范）` | 已核对规范或官方文档原文，§13 注明出处 |
| `已核实（实测）` | 已由附录 B 的实测数据支撑 |
| `已核实（选题）` | 来源为教师给定的选题描述，属既定范围 |
| `待核实（访谈）` | 核实计划为完成用户访谈，见 §14 |
| `待核实（实测）` | 核实计划为完成专项实测 |

# 1. 背景与问题陈述

> **本章为背景信息，用于说明「为什么做」，不构成需求。** 需求条目自第 4 章起。

## 1.1 问题背景

学生与知识工作者的知识积累具有三个特征：**来源多样**（课件、论文、网页、书籍、代码片段）、**周期长**（跨越整个学业或职业生涯）、**复用率高**（写作、复习、检索时反复调用）。当前主流的记录方式难以同时满足这三者：

- **记录分散**：笔记散落在 Word 文档、云笔记、聊天软件收藏、纸质本中，跨应用检索在物理上不可能实现。
- **格式私有**：多数云笔记服务使用私有存储格式，导出能力受限，用户数据的可迁移性依赖厂商意愿。
- **服务依赖**：云笔记工具一旦停服、涨价或限制免费额度，用户的全部积累面临失联风险。
- **组织方式单一**：以文件夹或标签为主的线性组织方式，难以表达笔记之间的引用与关联关系。
- **规模增长后性能下降**：当笔记量达到数万条时，部分工具的检索与打开速度显著退化。**本项已由附录 B 实测获得量化依据**：在 10 万篇、514.5 MB 的中文语料上，无索引的全量扫描完成一次检索的 P50 均值为 **8950 ms**，且**耗时与命中数量无关**（命中 1 篇的罕见词同样需要约 8 秒）；而 trigram 倒排索引完成同样查询的完整计数耗时均值为 **4.6 ms**，约快 **1900 倍**。

## 1.2 项目定位

本项目采用 **本地优先（local-first）** 的设计取向：笔记以标准 Markdown 纯文本文件的形式存储在用户本地文件系统，用户对自己的数据拥有完全的控制权，任何外部工具都可以直接读写这些文件。应用本身是这些文件的**编辑器与索引器**，而不是数据的持有者。

这一取向直接决定了后续多条基础性业务规则（见 BR-01、BR-03）。

## 2.3 主要使用场景

### S1 课堂快速记录（U1）
- **前置**：应用已在后台运行；学生正在听课。
- **主流程**：全局快捷键唤出快速记录窗口 → 输入内容 → `Esc` 关闭并自动落盘 → 课后在文件树中归档到课程目录。
- **异常**：全局快捷键被其他软件占用 → 提供可更换快捷键的设置项并给出冲突提示。
- **关联需求**：FR-EDT-01、FR-EDT-03、FR-SET-05。

### S2 文献整理与建立关联（U2）
- **前置**：库中已有若干文献笔记。
- **主流程**：新建文献笔记 → 填写 frontmatter 元数据 → 用 `[[笔记名]]` 链接到相关概念笔记 → 打开反向链接面板确认关联已被识别。
- **异常**：链接目标不存在 → 提示是否创建新笔记；存在多个同名笔记 → 提示歧义并要求用户确认（见 BR-04）。
- **关联需求**：FR-ORG-04、FR-LNK-01、FR-LNK-02。

### S3 跨库检索与复习（U1/U2）
- **前置**：库中笔记量达到数千条以上。
- **主流程**：输入关键词 → 结果按相关度排序并高亮命中片段 → 用 `tag:` 与 `path:` 组合过滤 → 回车打开笔记并定位到命中位置。
- **异常**：索引尚未建立完成 → 显示索引进度并允许先返回未索引的粗略结果；索引损坏 → 自动重建（见 BR-05）。
- **关联需求**：FR-SRC-01、FR-SRC-03、FR-SRC-04、TR-02。

### S4 草稿导出与投稿（U4）
- **前置**：长文草稿已完成并包含若干图片。
- **主流程**：选择导出 PDF → 选择 A4 模板 → 生成包含目录与页码的文件 → 打开确认排版正确。
- **异常**：图片为绝对路径且文件已被移动 → 导出报告缺失资源清单，不静默丢弃。
- **关联需求**：FR-IO-01、NFR-CMP-02。

### S5 多设备同步（U3）
- **前置**：两台设备均已配置同一个用户自备的同步目标。
- **主流程**：设备 A 修改笔记 → 关闭前同步完成 → 设备 B 打开时自动拉取 → 内容一致。
- **异常**：两端离线各改同一篇 → 联网后产生冲突 → 系统保留两份并提示人工合并（见 FR-SYN-02）。
- **关联需求**：FR-SYN-01、FR-SYN-02、FR-SYN-03。

# 7. 业务规则

> 业务规则是跨功能点的约束，功能需求不得与其冲突。

| ID | 规则 | 理由 |
|---|---|---|
| BR-01 | **文件即数据源**：磁盘上的 `.md` 文件是唯一权威数据源；应用内部的数据库仅为可重建的索引缓存。删除索引不得影响任何笔记内容。 | 本地优先定位的基础，也是数据安全的最后保证 |
| BR-02 | **绝不覆盖**：任何创建、复制、重命名、恢复操作遇到同名文件时，一律自动追加序号后缀（`名称 (2).md`），不提示覆盖、不静默覆盖。 | 笔记是长期积累资产，覆盖造成的损失不可逆 |
| BR-03 | **开放格式**：全部笔记与元数据均以标准纯文本格式存储，任何外部编辑器可读写；不使用私有二进制格式作为知识数据的载体。 | 保证用户数据主权与工具可替代性 |
| BR-04 | **链接消歧**：`[[A]]` 优先匹配库内同名文件；存在多个同名文件时，优先匹配与当前文件路径距离最近者，同时在界面标注歧义并提供选择入口，不静默任选。 | 双链的确定性是可信赖引用的前提 |
| BR-05 | **索引可丢弃**：索引损坏或版本不兼容时，系统自动重建，不将其作为错误上报给用户，仅记入日志。 | 索引是缓存而非数据，不应污染用户对数据安全性的判断 |
| BR-06 | **同步不合并**：本版本中同步冲突一律通过保留双份解决，不自动进行字符级合并。 | 自动合并出错时用户难以察觉，风险高于人工合并的麻烦 |
| BR-07 | **删除即移动**：删除操作在保留期内为移动到回收站，不执行真实的文件系统删除；彻底删除须用户二次确认。 | 与 BR-02 同源：不可逆操作必须显式确认 |
| BR-08 | **无账号**：应用不建立账号体系，不采集用户身份信息，核心功能全部离线可用。 | 与 §1.2 定位一致，同时消除隐私合规负担 |

### 弹性区约定（v0.2 新增）

范围弹性区指**可整体延后至下一版本、且延后不影响其余功能可用性**的模块。弹性区与其优先级必须一致：

1. 弹性区模块内的条目一律评为**低**（判据 ⑤），因为「可延后」意味着「缺失可用替代手段绕行」。
2. 若某条目被提升至中或高，则该模块不再构成弹性区，须在 §12 边界中相应调整。
3. 本版本弹性区为 **M7 同步模块**；其条目全部为低，与规则 1 一致。若 M7 纳入交付版本，则 FR-SYN-02 依判据 ④ 升为中，同时 §12 中 OUT 相关条目须修订。

# 8. 输入输出数据格式

## 8.1 笔记文件

| 项 | 规定 |
|---|---|
| 扩展名 | `.md` |
| 编码 | UTF-8，**不写入 BOM**；读取时容忍 BOM 与非法字节并提示 |
| 换行符 | 读取时保留原有风格（LF 或 CRLF）；新建文件使用 LF |
| 元数据 | 文件头部可选的 YAML frontmatter，以 `---` 独立行包裹，位于文件第 1 行 |
| 正文 | 附录 A 锁定的 Markdown 子集 |
| 文件大小上限 | 单篇 ≤ 10 MB（见 **CON-06**） |

## 8.2 frontmatter 字段定义

| 字段 | 类型 | 必填 | 示例 | 说明 |
|---|---|---|---|---|
| `title` | 字符串 | 否 | `二叉搜索树` | 缺省时以文件名为标题 |
| `tags` | 字符串数组 | 否 | `[数据结构, 复习]` | 层级标签用 `/` 分隔（FR-ORG-02） |
| `aliases` | 字符串数组 | 否 | `[BST, 二叉查找树]` | 供 `[[...]]` 链接解析使用的别名 |
| `created` | 字符串 | 否 | `2026-09-28T14:30:00+08:00` | ISO 8601 带时区偏移（TR-08） |
| `updated` | 字符串 | 否 | `2026-09-28T16:05:00+08:00` | 由应用维护，不建议手改 |
| `favorite` | 布尔 | 否 | `true` | 收藏标记（FR-ORG-05），存于文件而非私有库 |
| `status` | 字符串 | 否 | `草稿 / 整理中 / 完成` | 自定义枚举，取值由用户自行约定 |

**解析容错规定**：frontmatter 无法解析为合法 YAML 时，应用须将整篇文件按纯正文处理，在属性面板给出定位到行的错误提示，且**保存时不得重写或删除该段内容**。

## 8.3 附件

| 项 | 规定 |
|---|---|
| 存储位置 | 库内配置的附件目录（默认 `attachments/`），可配置为与笔记同目录 |
| 命名规则 | `{yyyyMMddHHmmss}-{原文件名}`；重名时按 BR-02 追加序号 |
| 引用方式 | 正文中使用相对路径引用，保证库整体移动或导出后链接仍有效 |

## 8.4 备份包

```
backup-20260928-120000.zip
├── manifest.json          备份清单
├── notes/                 笔记原文，保留库内相对路径
└── attachments/           附件，保留相对路径
```

`manifest.json` 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `formatVersion` | 整数 | 备份包格式版本，用于恢复时的兼容性判断 |
| `createdAt` | 字符串 | ISO 8601 带时区偏移 |
| `noteCount` | 整数 | 笔记数量 |
| `attachmentCount` | 整数 | 附件数量 |
| `checksum` | 字符串 | 内容的校验摘要，用于恢复前完整性校验 |

## 8.5 导出格式

| 目标格式 | 规定 |
|---|---|
| Markdown | 正文原文，链接改为相对路径，附件随包导出 |
| HTML | 单文件，图片以 base64 内联，不依赖外部资源；输出符合附录 A 子集的渲染结果 |
| PDF | A4，含目录与页码，代码块保留语法高亮 |

## 8.6 同步元数据

同步以文件为单元，每个文件的同步状态（内容哈希、修改时间、设备标识）记录于库内独立的元数据文件中。**该文件属内部实现细节，不作为对外接口，不承诺跨版本兼容**；但须满足 NFR-MNT-02：其存在不得改变笔记文件本身的格式。

# 10. 验收标准

## 编号规则

用例编号统一为 `TC-⟨需求ID⟩-⟨序号⟩`，如 `TC-EDT-01-1` 表示 FR-EDT-01 的第 1 个用例。**每条功能需求至少 1 个用例，每条非功能需求至少 1 个测量用例。** 前置条件、操作、预期结果三列均为必填，预期结果须给出**可观察、可判定**的描述。

# 12. 边界与范围外事项

| 编号 | 范围外事项 | 理由 |
|---|---|---|
| OUT-01 | **移动端原生应用** | 本地优先定位依赖对本地文件系统的直接访问，移动端沙箱机制限制严格；且移动端场景与「桌面知识库」的主场景（长时间整理与写作）差异显著。**该判断待问卷核实**：若用户对移动端的需求强度超出预期，须修订本项目范围说明 |
| OUT-02 | **多人实时协作** | 实时协作需要中心化的权限与并发控制，与本地优先、无账号的架构取向直接冲突。本项目定位为个人知识管理工具 |
| OUT-03 | **自建云服务与账号体系** | 见 BR-08。具体不做的内容包括：不提供注册登录、不托管用户数据、不运营任何服务端。**理由**：自建服务会引入数据托管责任、运维成本与隐私合规负担；而同步能力改由用户自备的第三方存储承担（见 FR-SYN-01），二者分工明确——本应用只负责读写用户指定的存储位置 |
| OUT-04 | **插件系统与开放 API** | 具体不做的内容包括：不提供插件加载机制、不发布对外 API、**不承诺任何扩展接口的稳定性**。**理由**：插件沙箱安全与 API 兼容性维护的成本超出个人开发范围，且核心价值不依赖插件。保留设计上的扩展点（如模板占位符、frontmatter 自定义字段），但这些是数据层的可扩展性，不构成编程接口 |
| OUT-05 | **字符级自动冲突合并（CRDT 类方案）** | 实现复杂度高，且合并出错时用户难以察觉，风险高于人工合并的麻烦。V1 采用「保留冲突副本 + 人工合并」（BR-06），可满足单用户多设备场景 |
| OUT-06 | **端到端加密同步** | 同步目标为用户自备存储，加密责任可移交用户（如使用支持加密的 WebDAV 服务）。若在本应用内实现，须一并解决密钥管理与恢复问题，成本过高 |
| OUT-07 | **PDF / 图片 OCR、手写识别、语音转写** | 属于内容生产环节，与本项目「记录与组织」的核心定位正交 |
| OUT-08 | **Web 版** | 浏览器无法直接读写用户本地文件系统，「本地优先」在 Web 形态下无法成立 |
| OUT-09 | **笔记内容的多端实时协同编辑、评论、@提及** | 属于协作类能力，与 OUT-02 同源 |
| OUT-10 | **任务管理与日程规划（待办、日历视图、提醒推送）** | 与笔记工具的定位相邻但不同；纳入会导致范围蔓延。用户可通过导出 Markdown 交由专业工具处理 |
| OUT-11 | **数学公式（LaTeX）渲染** | 附录 A 清单外的语法，按 EX-19 降级为原文保留。**理由**：公式渲染需引入独立的排版引擎，与「纯文本可互操作」的目标存在取舍；本版本按普通文本保留原始 LaTeX 源码，保证数据不丢失 |
| OUT-12 | **脚注语法** | 脚注既不属于 CommonMark 核心规范，也不属于 GFM 扩展（经核对两个规范原文确认）。同按 EX-19 保留原文。**该条为 v0.2 新增：v0.1 曾将「脚注」误列为受支持的语法，已纠正** |

| 算法 | 78148 | 78148 | **完整** | 670 ms |
| 索引 | 53017 | 53017 | **完整** | 742 ms |

**结论**：两字查询存在**可行且召回正确**的回退路径，耗时 670–742 ms。相对无索引全量扫描的 8950 ms 仍快约 **12 倍**，可作为可接受的降级方案（NFR-PER-01 为短查询单独设定 ≤ 1 s 的预算即来源于此）。

## B.8 结论与对需求的影响

| # | 结论 | 对需求文档的影响 |
|---|---|---|
| 1 | 无索引方案在 10 万篇规模下检索需约 8–10 秒，且耗时与命中数无关 | 证明索引是功能前提；作为 §1.1 问题 P4 的量化支撑 |
| 2 | unicode61 对中文召回率仅 4.5%–4.6%，跨词边界与两字查询零召回 | **方案否决**；WRITTEN INTO FR-SRC-05 的技术约束 |
| 3 | trigram 对 ≥ 3 字符查询召回 100% 正确，完整计数 1.9–6.1 ms，首屏 P95 ≤ 0.9 ms | NFR-PER-01（长查询）定为 P95 ≤ 50 ms，留足余量 |
| 4 | trigram 对 < 3 字符查询**静默返回 0**——是正确性缺陷，不是性能缺陷 | 新增 **EX-21**：禁止把「索引无法服务」表现为「无结果」，并要求状态可区分 |
| 5 | 两字查询存在可行回退路径（LIKE 全表匹配，召回 100%，670–742 ms） | **FR-SRC-05 重写为双路径策略**；NFR-PER-01 为短查询单独设 ≤ 1 s 预算 |
| 6 | trigram 建库 28.3 分钟、索引体积 2.48 倍语料 | **NFR-PER-04 由「≤ 5 分钟」修订为「≤ 30 分钟」**——v0.1 的 5 分钟目标经实测判定不可达；新增 **NFR-PER-06**（索引体积 ≤ 语料 3 倍）；新增 **EX-22**（重建期间的行为） |
| 7 | 语料为模板化生成，词汇分布均匀 | 已写入 §B.2 局限说明：绝对耗时可参考，文档频率与耗时的关系不可外推 |

**技术选型结论**：SQLite FTS5 trigram 可作为原型阶段的检索方案，但**必须自行实现短查询回退路径**，且必须接受全量重建 28 分钟的成本（日常依赖增量索引，见 TR-02）。生产方案应评估自建二元组索引等替代路径——该评估不在本次范围内。

## B.9 本实测未能覆盖的部分（如实列明）

1. **单篇 ≤ 1 MB 的输入延迟（NFR-PER-03）**：本实测测量的是检索路径，编辑路径的输入延迟取决于编辑器实现，**未测量**。当前判定为**待核实**。
2. **常规使用下的内存占用（NFR-PER-05）**：本次尝试采集峰值工作集**未能成功**（采集函数返回 0），且即使采集成功，原型进程也不含编辑器渲染层，不能代表真实应用。当前判定为**待核实**。
3. **完整冷启动（NFR-PER-02）**：本实测测的是「打开索引 + 首次查询」耗时（645 ms），是冷启动的主要组成部分但**不等同于完整冷启动**。指标已据此部分标定，仍须在原型阶段复测。
4. **增量索引时延（FR-SRC-02、TR-02）**：本次测的是全量建库，**未测增量路径**。1 秒的增量时延指标仍为待核实。
5. **网络盘行为（EX-14、NFR-CMP-01）**：本次未在真实网络盘上复现变更通知失败与缓冲区溢出的情形。该条依据的是 Microsoft 官方文档，**属文档依据而非实测依据**，已在 EX-14 中如实标注。
6. **真实笔记库的长尾词汇分布**：本语料由 120 个词的词池模板化生成，词汇分布均匀（常见词文档频率集中在 52%–78%），与真实笔记库的长尾分布差异显著。

## B.10 增量索引时延实测

测量内容：单篇笔记内容变更后，完成「读取文件 → 删除旧索引行 → 插入新行 → 提交」的耗时。**不含文件系统监视与防抖**，因此它是端到端时延的**下界**。

| 项 | 第一轮 | 复测 |
|---|---|---|
| 样本量 | 100 | 100 |
| P50 | 431 ms | 433 ms |
| P95 | 455 ms | 453 ms |
| Max | **10650 ms** | 466 ms |
| 超过 1 s 的样本数 | **1** | 0 |

**结论**：

1. 主体耗时约 **430–455 ms**，在 TR-02 的 1 秒预算内，但**已占用约一半预算**，剩余空间需留给文件监视、防抖与队列调度。这是 TR-02 将「1 秒」保留而非收紧的依据。
2. 首轮出现 1 次 **10.6 秒尖峰**，复测 100 次未复现。推测为索引段合并或首次提交触发的检查点操作。**因为尖峰是间歇性的，不能假设它不会发生**——这构成 TEC-04（索引更新必须异步执行、不得阻塞编辑输入）的直接依据。
3. 本测量是下界，端到端时延（含文件监视与防抖）仍须在原型阶段复测。该项在 §14 与《人工核实说明》§6 中登记为待完成。
