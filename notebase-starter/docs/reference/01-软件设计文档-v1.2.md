# 1. 设计目标、边界与需求基线

## 1.1 设计目标

在满足 82 条需求基线的前提下，交付一个**可在单机离线运行、对 10 万篇笔记仍可用**的桌面应用设计。设计的核心矛盾有三个，后文所有关键决策都围绕它们展开：

1. **数据主权 vs 可用性**：文件是唯一数据源（BR-01），因此索引只能做缓存，任何索引结构都必须可丢弃、可重建（BR-05）。
2. **中文检索的正确性 vs 性能**：实测表明没有单一索引方案能同时满足「跨词边界子串」与「两字词」两类查询（见 §9 D-03）。
3. **单篇编辑的低延迟 vs 全库索引的高成本**：实测显示全量重建需 28.3 分钟，因此日常路径必须完全依赖增量索引（§9 D-11）。

## 1.2 设计边界

| 项 | 本文档负责 | 不在本文档范围 |
|---|---|---|
| 范围 | 架构、模块、流程、接口、数据、界面要点、非功能应对、异常处理、决策、追溯、验证 | 具体代码实现、详细视觉设计稿、运维部署脚本 |
| 平台 | Windows 10/11（第一优先）、macOS 12+、Linux 桌面（CON-02） | 移动端（OUT-01）、Web 版（OUT-08） |
| 依赖 | 文件系统、SQLite、平台 WebView、OS 凭据库、用户自备 WebDAV | 自建服务端（OUT-03）、账号体系（BR-08） |

## 1.3 需求基线来源

需求基线来自《需求分析文档》v0.3，其编号体系与内容摘要见配套文件《需求基线与变更说明》v1.0。本文档不重复罗列全部需求正文，仅在追溯矩阵中引用编号。

## 1.4 基线一致性核对（设计阶段执行）

设计开始前对基线做了一次逐项核对，确认设计与基线不冲突。核对结果如下，**未发现需要变更的需求**：

| 核对项 | 结论 | 说明 |
|---|---|---|
| FR-EDT-02 的 Markdown 子集（附录 A） | 一致 | 选型 comrak 支持全部 5 项 GFM 扩展；其**非 GFM 扩展（脚注、定义列表、上标）必须显式关闭**，否则会与附录 A §A.5「明确不在子集内」冲突。已在 §5.5.3 写入配置约束 |
| FR-SRC-05 + NFR-PER-01 的短查询预算 | 一致 | 设计要求 <3 字查询走「标题快路径 + 正文扫描」，实测同规模扫描 670–742 ms，在 ≤1 s 预算内 |
| NFR-PER-04 的 30 分钟重建预算 | 一致但紧张 | 实测 28.3 分钟已达基线值的 94%，设计采用分块事务 + 断点续建把风险前移（§8.1 风险 R-02） |
| NFR-PER-06 的索引体积 ≤3 倍 | 一致 | 实测 trigram 索引 2.48 倍，余量 0.52 倍 |
| FR-IO-01 的 PDF 导出 | 一致但分平台 | PDF 依赖平台 WebView 的打印能力；Windows 由 WebView2 `PrintToPdfAsync` 提供（已核实官方文档），macOS/Linux 需在 M2 阶段验证，不可用时的降级路径已定义（§5.6.4、D-10） |
| BR-01 / BR-05 的数据源定位 | 一致 | 索引库存放在应用数据目录而非库目录，进一步强化「索引不属于数据」的语义（D-05） |
| CON-05 的 20 万篇上限 | 存在规模风险，非需求冲突 | 性能指标均在 10 万篇标定；20 万篇时短查询扫描约 1.4 s，**超出 NFR-PER-01 的 1 s**。处理方式见 §8.1 风险 R-01，属于已知上限而非需求缺陷 |

> 结论：**无需变更需求。** 上表第 7 项是一个需要记录的边界（指标在 10 万篇标定，20 万篇为设计上限但不承诺同等时延），已在 §8.7 与《需求基线与变更说明》§4 中说明。

# 2. 架构设计

## 2.1 架构风格与总体分层

采用**四层分层架构**（表现层 / 应用层 / 领域层 / 基础设施层），层内按职责拆组件，层间只允许单向依赖。选择分层而非微服务、事件总线或插件化架构，理由是单人开发规模下，分层足以隔离变化点，其他风格属于过度设计（评审点：架构与选题规模相匹配）。

```
┌───────────────────────────────────────────────────────────────┐
│ L1 表现层  ui (WebView)                                        │
│    编辑器 / 文件树 / 检索面板 / 反向链接 / 设置 / 状态栏          │
└───────────────────────────┬───────────────────────────────────┘
                            │ IPC（命令 + 事件，JSON）
┌───────────────────────────┴───────────────────────────────────┐
│ L2 应用层  app-shell + services                                │
│    命令路由 / 用例编排 / 事务边界 / 事件分发                      │
│    note-svc  search-svc  link-svc  sync-svc  backup-svc  export-svc │
└───────────────────────────┬───────────────────────────────────┘
                            │ 仅依赖端口（trait）
┌───────────────────────────┴───────────────────────────────────┐
│ L3 领域层  domain                                              │
│    Note / Link / Tag / PathRules / SearchQuery / Conflict      │
│    BR-01 ~ BR-08 的规则实现（不含 I/O）                          │
└───────────────────────────┬───────────────────────────────────┘
                            │ 由基础设施实现端口
┌───────────────────────────┴───────────────────────────────────┐
│ L4 基础设施层  infra                                           │
│    fs-store  index-store  watcher  webdav-sync  keychain-store │
│    renderer  pdf-exporter  logger                              │
└───────────────────────────────────────────────────────────────┘
```

**依赖规则（架构约束，可在代码评审中机械检查）**：

| 规则 | 内容 | 违规示例（禁止） |
|---|---|---|
| R1 | L1 不得直接访问文件系统或数据库，只能通过 IPC | 前端直接读 `index.db` |
| R2 | L2 只能通过 L3 的领域对象与 L4 的端口接口交互，不得出现具体实现类型 | `note_svc` 直接 `use sqlite_index::...` |
| R3 | L3 不得依赖任何 I/O 库；时间、随机、文件访问一律经端口注入 | domain 里调用 `std::fs` |
| R4 | L4 之间不得互相调用，需要协作时由 L2 编排 | `watcher` 直接调用 `index-store` |
| R5 | 跨层只传值对象或 DTO，不传数据库行 | 把 `rusqlite::Row` 传到 L2 |

## 2.2 组件划分与职责

| 编号 | 组件 | 层 | 职责（单一） | 不负责 |
|---|---|---|---|---|
| C-01 | `ui` | L1 | 渲染界面、收集输入、维护视图状态、展示错误与进度 | 不含业务规则；不直接读写文件 |
| C-02 | `app-shell` | L2 | 窗口与菜单、全局快捷键、生命周期、IPC 路由、依赖装配 | 不含业务逻辑 |
| C-03 | `note-svc` | L2 | 笔记的创建/读取/保存/删除/恢复/重命名的用例编排与事务边界 | 不解析 Markdown 结构（交给 `link-svc` 与 `renderer`） |
| C-04 | `search-svc` | L2 | 查询解析、路由（长/短查询）、结果排序与分页、降级标记 | 不实现索引存储（交给 `index-store`） |
| C-05 | `link-svc` | L2 | `[[...]]` 解析、目标消歧、反向链接、重命名联动 | 不写文件（经 `note-svc`） |
| C-06 | `sync-svc` | L2 | 三方比对、冲突判定、重试调度、同步状态机 | 不实现传输（交给 `SyncBackend`） |
| C-07 | `backup-svc` | L2 | 备份包生成/校验/恢复、恢复前快照 | 不做增量备份（V1 全量） |
| C-08 | `export-svc` | L2 | 导出编排、资源缺失报告 | 不渲染 Markdown（交给 `renderer`） |
| C-09 | `index-worker` | L4 | 索引写入的唯一入口，串行执行增量与全量重建，发出进度事件 | 不做查询（查询由 `search-svc` 经端口发起） |
| C-10 | `watcher` | L4 | 文件系统事件采集、防抖、溢出检测、轮询降级 | 不解析文件内容 |
| C-11 | `fs-store` | L4 | 原子写入、路径合法化、编码与换行处理、文件枚举 | 不懂笔记语义 |
| C-12 | `index-store` | L4 | SQLite 模式管理、迁移、FTS5 读写、查询执行 | 不决定查询语义 |
| C-13 | `webdav-sync` | L4 | WebDAV 协议实现 | 不做冲突判定 |
| C-14 | `keychain-store` | L4 | 凭据存取（平台凭据库） | 不保存业务配置 |
| C-15 | `renderer` | L4 | Markdown → HTML（comrak，锁定扩展集） | 不做导出格式转换 |
| C-16 | `pdf-exporter` | L4 | 平台 WebView 打印到 PDF | 不做排版设计 |
| C-17 | `logger` | L4 | 结构化日志、脱敏、滚动与保留 | 不上报（NFR-SEC-01） |

**为什么把 `index-worker` 单独拿出来**：索引写入必须串行（SQLite 单写者 + FTS5 段合并会放大写放大），且必须异步（实测单次提交 P50 431 ms，尾部尖峰 10.6 s，见需求文档 §B.10）。把它做成独立线程并独占一个写连接，是同时满足 TR-02 与 TEC-04 的最小设计。

## 2.3 依赖关系

```
ui ──IPC──> app-shell ──> note-svc ──> NoteStore(port) ──> fs-store
                     ├──> search-svc ─> IndexStore(port) ─> index-store
                     ├──> link-svc ───> NoteStore / IndexStore
                     ├──> sync-svc ───> SyncBackend(port) ─> webdav-sync
                     │                  └> CredentialStore(port) ─> keychain-store
                     ├──> backup-svc ─> NoteStore / Exporter
                     └──> export-svc ─> Renderer(port) ─> renderer
                                        └> PdfExporter(port) ─> pdf-exporter
app-shell ──spawn──> index-worker ──> IndexStore
app-shell ──spawn──> watcher ──> Watcher(port) ──> fs 事件源
```

**循环依赖检查**：图中无环。`link-svc` 同时依赖 `NoteStore` 与 `IndexStore` 是必要的——重命名既要改文件也要改索引，二者必须在一个事务边界内编排，这是 `link-svc` 而非 `note-svc` 承担该职责的原因。


**部署要点**：

1. **单进程多线程**，不拆分守护进程。理由：进程间通信会引入额外故障面（孤儿进程、启动顺序），而本地优先场景无跨用户共享需求。
2. **库目录与应用数据目录分离**。库目录只放用户资产（`.md` + `attachments/`），不含任何应用私有文件；`index.db`、`drafts/`、`logs/` 放在应用数据目录（Windows `%APPDATA%\NoteBase\`，macOS `~/Library/Application Support/NoteBase/`，Linux `$XDG_DATA_HOME/notebase/`）。这一条同时满足 BR-03 与「备份包不在库内」（FR-BAK-01）。
3. **索引可按库重建**：应用数据目录以 `vaults/<vault_id>/` 分目录，`vault_id = sha256(规范化绝对路径)` 前 16 位。库被移动或拷贝到另一台机器时索引丢失，按 BR-05 自动重建，不视为错误。
4. **无服务端**：除用户显式配置的 WebDAV 外不存在任何外联（NFR-SEC-01）。

## 2.5 运行视图（线程与生命周期）

| 执行体 | 类型 | 职责 | 并发约束 |
|---|---|---|---|
| 主线程 | UI 事件循环 | 窗口、菜单、IPC 收发、快照更新 | 单线程 |
| `index-writer` | 专用线程（1 个） | 增量/全量索引写入 | **单写者**，独占写连接 |
| `index-reader` | 连接池（N=2） | 检索查询 | 只读连接，WAL 快照隔离 |
| `watcher` | 专用线程（1 个） | 文件事件 → 防抖队列 | 队列容量 4096，溢出即触发全量对账 |
| `sync-runner` | 异步任务（1 个） | 同步状态机 | 单实例，重入时返回 `E_SYNC_BUSY` |
| `render-pool` | 线程池（N=2） | 预览渲染、导出渲染 | 同一笔记的渲染请求去重（按 path+hash） |
| `backup-runner` | 异步任务（1 个） | 备份与恢复 | 恢复期间暂停索引写入 |

**启动序列**（对应 F-01）：

```
1 读取 settings.json
2 定位库目录 → 不存在则走 EX-08 引导
3 打开 index.db（只读打开 + 校验 schema_version）
4 呈现主窗口骨架（≤ 300 ms，不等待索引）
5 挂载文件监视
6 发出 index.state
7 若 schema 不匹配或库不可读 → 后台重建（BR-05）
```

**退出序列**：冲刷草稿 → 停止 watcher → 排空索引写队列 → `PRAGMA wal_checkpoint(TRUNCATE)` → 关闭窗口。超过 3 秒未完成则强制退出，依赖 WAL 恢复。

## 3.2 `note-svc` 内部结构

三个协作者，职责不重叠：

- **`WriteGuard`**：以 `path` 为键的互斥锁集合，保证同一笔记不会有两个并发保存写入。另维护「最近一次已知磁盘哈希」，用于识别外部修改（EX-03）。
- **`AtomicWriter`**：写入流程固定为「同目录临时文件 → 写入 → `fsync` → `rename` 覆盖 → 目录 `fsync`」。任一步失败删除临时文件并返回错误。这条直接对应 NFR-REL-02。
- **`DraftManager`**：编辑期间每 500 ms 将未落盘内容写入 `drafts/<sha256(path)>.json`，正常保存后删除。崩溃恢复时比较草稿与磁盘内容（§F-04）。

**保存用例的判定表**（这是 `note-svc` 唯一的复杂逻辑，必须显式定义，否则 EX-03 无法实现）：

| 磁盘哈希 vs 已知哈希 | 请求 baseHash vs 已知哈希 | 判定 | 动作 |
|---|---|---|---|
| 相同 | 相同 | 正常保存 | 写入 |
| 相同 | 不同 | 客户端基于旧版本 | 拒绝，返回 `E_STALE_CLIENT` |
| 不同 | 相同 | 磁盘被外部修改 | 拒绝，返回 `E_EXTERNAL_MODIFIED` + 三个选项（EX-03） |
| 不同 | 不同 | 双方都改了 | 拒绝，返回 `E_EXTERNAL_MODIFIED` 且 `concurrent=true` |
| 文件不存在 | 任意 | 已被删除 | 返回 `E_NOT_FOUND`，提供重建（EX-02） |

## 3.3 `search-svc` 内部结构

**查询路由**（核心设计，对应 FR-SRC-05 的三项条件）：

| 查询形态 | 路由 | 目标时延 | 实现 |
|---|---|---|---|
| 长度 ≥ 3（含中文、英文、混合） | 倒排索引 | 首屏 P95 ≤ 50 ms | `note_fts` MATCH，trigram |
| 长度 < 3（中文 1–2 字） | 双阶段：标题快路径 → 正文扫描 | 首屏 P95 ≤ 1 s | ① `notes.title` / `aliases` / `tags` 用 `LIKE`；② 在 `note_fts` 的**影子表 `note_fts_content`** 上 `LIKE` 扫描（表形态见 §6.4），流式返回 |
| 查询语法不支持（未闭合引号等） | 解析失败 | — | 返回 `E_QUERY_SYNTAX`，不回退为模糊匹配 |
| 空查询 | 空页 | — | 返回空页，不报错 |

**为什么短查询不用倒排索引**：实测 trigram 在查询词少于 3 个字符时无法生成三元组，会**静默返回 0 条**；unicode61 对中文的召回率只有 4.5%。因此短查询必须走扫描路径，这是由数据决定的，不是设计偏好（§9 D-03）。

**排序规则**：`score = 3×标题命中 + 2×别名命中 + 1×正文命中频次归一化 + 0.5×最近修改时间衰减`。标题/别名命中恒排在正文命中之前，保证短查询的「标题快路径」结果自然置顶。

**降级标记**：响应中 `degraded` 与 `degradeReason` 为必填字段；`degraded=true` 表示当前结果是部分索引或扫描中截断的结果。EX-21 要求「不可服务」与「无结果」可区分，实现方式是前者返回错误码 `E_QUERY_UNSUPPORTED`，后者返回 `items: []` 且 `ok: true`。

## 3.4 `link-svc` 内部结构

- **`WikiLinkParser`**：从正文提取 `[[target]]` 与 `[[target|alias]]`，记录 `line/col`。只识别附录 A 子集内的语法；`![[...]]`（内嵌文件与块引用）按**附录 A §A.5「内嵌文件与块引用」**保留原文、不建链——该条与 OUT-11 的 LaTeX 是两回事，v1.0 曾把二者合写为「OUT-11/A.5」，已修正。
- **`Resolver`**：按 BR-04 消歧——唯一同名直接解析；多个同名按「与源文件路径的公共前缀长度」最大者优先，并列则标记 `ambiguous=true`，界面呈现候选列表（EX-20）。
- **`BacklinkReader`**：查 `links` 表 `target_path = ?`，附上下文片段（前后各 40 字符）。
- **`RenamePropagator`**：两阶段——先写 `rename_journal`（源路径、目标路径、受影响文件清单、进度），再逐个文件改写并更新索引；中断后按日志续跑，保证幂等。

## 3.5 `sync-svc` 内部结构

**状态机**（`sync_state.state`）：`clean → dirty → pending → (clean | conflict)`。

| 状态 | 含义 | 迁移条件 |
|---|---|---|
| `clean` | 本地与远端一致 | 检测到本地变更 → `dirty` |
| `dirty` | 本地有未上传变更 | 同步任务取到 → `pending` |
| `pending` | 正在传输 | 成功 → `clean`；失败 → `dirty`（并计入重试次数） |
| `conflict` | 双端均改 | 人工处理后 → `dirty`，下次同步 → `clean` |

**三方比对**以 `sync_state.base_hash`（上次同步成功的哈希）为基准，这是能区分「本地删除」与「远端从未有过」的唯一依据。缺少 base 时，任何双端差异都判为冲突（保守策略）。

# 4. 关键流程设计

> 每个流程给出：触发条件、主路径（编号步骤，标注模块与数据操作）、分支路径、异常路径（对应需求文档 EX 编号）、结束状态。所有步骤中出现的接口名见 §5，数据表见 §6。

## F-01 启动与索引可用性

**触发**：用户启动应用。**前置**：无。

| 步骤 | 动作 | 模块 | 数据 |
|---|---|---|---|
| 1 | 读取配置，解析库路径 | app-shell / fs-store | `settings.json` |
| 2 | 校验库目录存在且可读 | fs-store | — |
| 3 | 打开 `index.db`，读 `meta.schema_version` | index-store | `meta` |
| 4 | 挂载监视，启动 index-worker | watcher / index-worker | — |
| 5 | 主窗口可交互，发出 `EVT-index.state` | ui | — |

**分支**：
- B1 版本匹配 → 正常进入。
- B2 版本不匹配或文件损坏 → **不报错**，后台重建（BR-05、EX-05），界面显示「正在重建索引」进度（`EVT-index.progress`）。
- B3 索引文件不存在（首次打开或换机器）→ 同 B2。

**异常**：
- EX-08 库目录不存在/被移动 → 返回 `E_VAULT_NOT_FOUND`，进入重新定位向导。
- EX-13 网络盘断连 → 连续 3 次读失败后切只读模式，发出 `EVT-index.state {mode:"offline"}`。

**结束状态**：应用可用；索引可能处于 `ready` / `rebuilding` / `offline` 之一。**首屏不等待索引**，这是满足 NFR-PER-02（≤2 s）的关键——实测索引打开本身需 645 ms，若串行等待则余量会被界面初始化吃掉。

## F-02 新建笔记

**触发**：`CMD-note_create`。**前置**：库已打开。

| 步骤 | 动作 | 模块 | 数据 |
|---|---|---|---|
| 1 | 生成默认文件名（首行标题或「未命名」） | note-svc | — |
| 2 | 路径合法化：非法字符替换、保留名处理、长度截断 | fs-store `PathValidator` | — |
| 3 | 同名检测：存在则追加 ` (2)` | fs-store | 目录枚举 |
| 4 | 原子创建空文件（`CreateNew`，若已存在则失败重试） | fs-store `AtomicWriter` | 文件 |
| 5 | 入队索引 | index-worker | `notes`、`note_fts` |
| 6 | 通知界面打开该笔记 | app-shell | `EVT-note.changed` |

**异常**：EX-01 磁盘满/无权限 → `E_IO_DISK_FULL` / `E_IO_PERMISSION`，界面提示且不留下半写文件。

## F-03 编辑与自动保存

**触发**：用户输入。**前置**：笔记已打开。

| 步骤 | 动作 | 模块 | 数据 |
|---|---|---|---|
| 1 | 输入进入前端缓冲，500 ms 无输入后写草稿 | ui / `DraftManager` | `drafts/<hash>.json` |
| 2 | 2 s 防抖触发保存请求（携带 `baseHash`） | ui → note-svc | — |
| 3 | 判定表校验（§3.2） | note-svc `WriteGuard` | — |
| 4 | 原子写入（临时文件 → fsync → rename） | fs-store | 文件 |
| 5 | 内容哈希变化则记一个快照 | backup-svc | `snapshot_index` + blob |
| 6 | 入队增量索引 | index-worker | `notes`、`note_fts`、`links`、`tags` |
| 7 | 若引用关系变化，刷新反向链接面板 | link-svc | `links` |

**分支**：
- B1 连续输入超过 10 s 未触发保存 → 强制落盘（TR-01）。
- B2 保存期间又有新输入 → `WriteGuard` 串行化，第二次保存基于新内容；界面不阻塞输入。

**异常**：
- EX-01 写失败 → 保留内存内容，切只读，暂停自动保存，提示「另存到其他位置」。
- EX-03 外部修改 → 三选项对话框（保留本地/保留磁盘/另存副本），见 F-06。
- EX-04 文件被占用 → 按 1/2/4/8/16 s 退避重试 5 次，超限转入待保存队列。

## F-04 崩溃恢复

**触发**：启动时发现草稿文件存在且比磁盘文件新。**前置**：上次非正常退出。

| 步骤 | 动作 | 模块 | 数据 |
|---|---|---|---|
| 1 | 扫描 `drafts/`，逐个读 `{path, body, baseHash, savedAtMs}` | note-svc `DraftManager` | `drafts/*.json` |
| 2 | 比较 `savedAtMs` 与磁盘 `mtime`，以及 `baseHash` 与磁盘当前哈希 | note-svc | 文件元数据 |
| 3 | 草稿更新且基哈希一致 → 判定可恢复 | note-svc | — |
| 4 | 界面列出可恢复项，用户逐条确认 | ui | — |
| 5 | 确认后走 F-03 的保存路径，成功后删除草稿 | note-svc | 文件、草稿 |

**异常**：草稿与磁盘哈希均不同 → 判定为「草稿 + 磁盘双改」，保留两份（磁盘原文 + 恢复副本），交用户处理，不静默覆盖（BR-02 的延伸）。

**可度量目标**：自动保存窗口（≤2 s）内的内容可恢复率 ≥99%（NFR-REL-01）。设计手段是 500 ms 草稿落盘，使最坏丢失窗口为 500 ms，而不是 2 s。

## F-05 检索

**触发**：`CMD-search`。**前置**：索引处于 `ready` 或 `rebuilding`。

| 步骤 | 动作 | 模块 | 数据 |
|---|---|---|---|
| 1 | 解析查询：去首尾空白、NFKC 归一化、拆出语法成分 | search-svc `QueryParser` | — |
| 2 | 按长度路由（§3.3） | search-svc `QueryRouter` | — |
| 3a | 长查询：`note_fts MATCH` + 过滤条件 JOIN | index-store | `note_fts`、`notes`、`tags` |
| 3b | 短查询阶段一：标题/别名/标签 `LIKE`，立即返回 | index-store | `notes`、`aliases`、`tags` |
| 3c | 短查询阶段二：在 `note_fts` 的影子表上做正文 `LIKE` 扫描，流式补充 | index-store | `note_fts_content`（影子表） |
| 4 | 排序、生成高亮片段 | search-svc `Ranker`/`SnippetBuilder` | — |
| 5 | 返回首页 + `nextCursor` | search-svc | — |

**分支**：
- B1 带过滤器（`tags` / `pathPrefix` / 时间范围 / `hasAttachment`）→ 在步骤 3 后追加 SQL 过滤，过滤在数据库内完成，不回到应用层筛。
- B2 `sort = mtime` → 跳过评分，按 `mtime_ms` 倒序。
- B3 索引重建中 → 结果标注 `degraded=true`，`degradeReason="index_rebuilding"`（EX-22）。

**异常**：
- EX-21 查询无法服务 → `E_QUERY_UNSUPPORTED`，**绝不返回空列表冒充无结果**。
- EX-05 索引损坏 → 自动重建，查询退化为扫描并标注降级。
- 超时：短查询超过 1 s 仍未完成 → 返回已有部分结果 + `degraded=true, degradeReason="scan_timeout"`。

| 3 | 发出 `EVT-note.conflict`，携带两侧哈希与修改时间 | app-shell | — |
| 4 | 界面展示三选项与差异预览 | ui | — |
| 5a | 保留本地 → 以 `baseHash=磁盘当前哈希` 强制写入 | note-svc | 文件 |
| 5b | 保留磁盘 → 丢弃内存内容，重新加载 | note-svc | — |

## F-07 双链创建与重命名联动

**触发 A**：正文输入 `[[` 后选择目标。**触发 B**：`CMD-note_rename`。

**A. 创建链接**

| 步骤 | 动作 | 模块 | 数据 |

| 3 | 保存后 `WikiLinkParser` 重新抽取链接 | link-svc | 读正文；产出链接列表（内存） |
| 4 | `Resolver` 解析目标；未解析则 `resolved=0` | link-svc | 读 `notes`、`aliases`；写 `links.target_path/resolved/ambiguous` |
| 5 | 更新 `links` 表，刷新目标笔记的反向链接 | index-worker / link-svc | 写 `links`；读 `links`（反向查询） |

**B. 重命名联动**

| 步骤 | 动作 | 模块 | 数据 |
|---|---|---|---|
| 1 | `planOnly=true` 预演：查 `links WHERE target_path = 旧路径` | link-svc | `links` |

## F-08 同步

**触发**：定时（默认 5 min）、手动、或应用退出前。**前置**：已配置 WebDAV 且凭据可用。

| 步骤 | 动作 | 模块 | 数据 |
|---|---|---|---|
| 1 | 取同步锁，状态置 `pending` | sync-svc | `sync_state` |
| 2 | 本地：枚举库内文件，计算哈希，与 `sync_state` 比对得出本地变更集 | sync-svc / fs-store | `sync_state` |
| 3 | 远端：`PROPFIND` 取文件清单与 ETag | webdav-sync | — |
| 4 | 三方比对（base = `base_hash`），生成上传/下载/冲突/删除四类动作 | sync-svc `ThreeWayComparator` | — |
| 5 | 按动作执行；上传带 `If-Match: <base etag>` | webdav-sync | — |
| 6 | 更新 `base_hash`、`remote_etag`、`last_synced_ms`，状态回 `clean` | sync-svc | `sync_state` |

**分支**：
- B1 双端均改且哈希不同 → 冲突：下载远端内容为 `<名称> (冲突副本 …).md`，本地保持原名，状态 `conflict`（BR-06、TR-07）。
- B2 本地删除 + 远端未改 → 写墓碑并删除远端；远端已改 → 视为冲突（保留远端）。
- B3 离线 → 所有待办进 `pending` 队列，界面持续显示待同步数（FR-SYN-04）。
- B4 排除规则命中（`FR-SYN-05`）→ 跳过，不计入动作。

**异常**：
- EX-07 网络不可达 → 退避 1/2/4/8/16 s 重试 5 次（TR-06），超限进队列。
- 凭据失效（401）→ **不重试**，直接转等待重新授权（避免账号锁定），发出 `EVT-sync.state {authRequired:true}`。
- 远端 412（If-Match 失败）→ 说明远端已被他人改动，本轮整体回退到 `dirty`，下次重新比对（避免覆盖对方）。

## F-09 导出

**触发**：`CMD-export_note`。**前置**：笔记可读。

| 步骤 | 动作 | 模块 | 数据 |
|---|---|---|---|
| 1 | 读取笔记与引用的附件 | export-svc / fs-store | 读 `notes`；读库内文件与 `attachments/` |
| 2 | **解析正文中的全部 `[[...]]`，按 `links` 表分类为「已解析 / 未解析 / 歧义」三类** | link-svc / `Resolver` | 读 `links`（`target_path`、`resolved`、`ambiguous`） |
| 3 | 按格式分派 | export-svc | — |
| 3a | Markdown：复制原文；**只对「已解析」链接改写为相对路径**，另两类保持原文不动 | `MdExporter` | 读正文；写目标 `.md` 与附件副本 |
| 3b | HTML：comrak 渲染 → 图片 base64 内联 → 单文件 | `HtmlExporter` / renderer | 读正文与附件字节；写单个 `.html` |
| 3c | PDF：渲染 HTML → 隐藏 WebView 打印 → 落盘 | `PdfExporter` / pdf-exporter | 读渲染结果；写 `.pdf` |
| 4 | 汇总缺失资源与链接异常两份清单 | `MissingAssetReporter` | 产出 `missingAssets[]` 与 `warnings[]`（内存，不落库） |
| 5 | 返回文件路径 + 两份清单 | export-svc | 返回 `ExportResult` |

**分支**：

- **B1 存在未解析链接**（目标不存在）→ 保留 `[[原文]]` 字面量，不做任何改写，逐条写入 `warnings[]`：`{kind:"unresolved_link", target:"...", line:12}`。**理由**：把未解析链接改写成纯文本会永久丢失链接意图，用户之后补建目标笔记时无法恢复关联。
- **B2 存在歧义链接**（多个同名目标）→ 按 BR-04 的消歧结果导出为**确定路径**，同时写入 `warnings[]`：`{kind:"ambiguous_link", target:"...", candidates:[...]}`，提示该链接的解释可能与作者本机不同。
- **B3 同一目标在不同机器上解析结果不同**（库结构差异）→ 属于 B2 的一种，按 B2 处理并记录候选列表。

**异常**：
- EX-16 图片缺失 → 导出继续，返回 `missingAssets[]`，界面列出（不静默丢弃）。
- EX-19 清单外语法的内容 → 原样保留，HTML/PDF 中按普通文本呈现。
- PDF 平台能力不可用（见 D-10）→ 返回 `E_PDF_UNSUPPORTED`，提示改用 HTML 导出。

## F-11 索引全量重建

**触发**：手动、schema 升级、索引损坏。**前置**：无。

| 步骤 | 动作 | 模块 | 数据 |
|---|---|---|---|
| 1 | 建临时库 `index.rebuild.db`，写 `meta` | index-worker | 新库 |
| 2 | 按目录分批（每批 200 篇）读取、解析、写入 | index-worker | `notes`、`note_fts`、`links`、`tags` |
| 3 | 每批提交后发出进度 | index-worker | `EVT-index.progress` |
| 4 | 完成后原子替换 `index.db`，重开连接 | index-worker | — |
| 5 | 失败或中断 → 保留临时库与进度标记，下次续建 | index-worker | `meta.rebuild_cursor` |

**设计要点**：重建期间**旧索引保持可查**，查询走旧库；这满足 FR-SRC-06 的「重建期间应用保持可用」，也满足 EX-22 的「结果可能不完整」提示需求。实测建库 28.3 分钟，分块 + 断点续建是为了在长任务中避免「一次失败全部重来」。

### 时序图一：编辑与自动保存（F-03）

```
UI              app-shell         note-svc            fs-store        index-worker
 |                  |                 |                   |                 |
 |--输入(seq=42)--->|                 |                   |                 |
 |                  |--CMD-note_save->|                   |                 |
 |                  |                 |--lock(path)       |                 |

 |                  |                 |   [不一致]-------->|--返回 E_EXTERNAL_MODIFIED

 |<--响应(seq=42)---|                 |                   |                 |
 |                  |<------------------EVT-index.state--------------------|
```

```
UI          sync-svc          fs-store        webdav-sync       index-worker

 |              |--lock(单实例)    |                |                 |
 |              |--list+stat----->|                |                 |
 |              |<--本地哈希表-----|                |                 |
 |              |--PROPFIND(Depth:1)-------------->|                 |
```

# 5. 接口设计

## 5.1 接口分层

| 层 | 接口形式 | 稳定性承诺 | 章节 |
|---|---|---|---|
| UI ↔ Core | IPC 命令与事件（JSON over Tauri） | 应用内稳定，随版本演进 | §5.2–§5.4 |
| 应用层 ↔ 领域/基础设施 | Rust trait（端口） | 内部接口，不承诺跨版本 | §5.5 |
| 外部系统 | 文件系统、SQLite、WebDAV、OS 凭据库、平台 WebView | 依第三方规范 | §5.6 |

## 5.2 IPC 协议规范

**请求信封**

```json
{ "id": "req-001", "command": "note_save", "payload": { }, "clientSeq": 42 }
```

**响应信封**

```json
{ "id": "req-001", "ok": true, "data": { } }
{ "id": "req-001", "ok": false, "error": { "code": "E_IO_DISK_FULL", "message": "磁盘空间不足", "detail": { "path": "a.md" }, "retryable": false } }
```

**事件信封**

```json
{ "event": "index.progress", "payload": { }, "tsMs": 1760000000000 }
```

### CMD-settings_set（keymap 写入示例，对应 FR-SET-03）

请求：

```json
{
  "values": {
    "keymap": { "newNote": "Ctrl+N", "search": "Ctrl+Shift+F", "save": "Ctrl+S" }
  }
}
```

成功响应：

```json
{ "ok": true, "data": { "applied": ["keymap"], "restartRequired": false } }
```

冲突失败（对应 FR-SET-03「冲突时给出提示」）：

```json
{
  "ok": false,
  "error": {
    "code": "E_KEYMAP_CONFLICT",
    "message": "快捷键 Ctrl+Shift+F 已被系统占用",
    "detail": { "action": "search", "accelerator": "Ctrl+Shift+F", "current": "Ctrl+Alt+F" },
    "retryable": false
  }
}
```

**语义**：`keymap` 按整对象替换而非增量合并——请求中缺省的项恢复默认值，避免用户删除某个绑定后旧值残留。冲突检测在写入前对**全部**绑定做一次检查，任一项冲突则**整体拒绝**（不部分生效），保证「要么全改、要么不改」。

## 5.4 事件定义

| 事件（文档标识） | 线上事件名 | 载荷 | 触发时机 | 订阅方 |
|---|---|---|---|---|
| `EVT-note.changed` | `note.changed` | `{path, source:'local'\|'external'\|'sync', contentHash}` | 文件内容变化后 | 编辑器、文件树、反向链接面板 |
| `EVT-note.conflict` | `note.conflict` | `{path, localHash, diskHash, concurrent:bool}` | 检出冲突 | 冲突对话框 |
| `EVT-index.progress` | `index.progress` | `{phase:'scan'\|'write'\|'optimize', done, total, elapsedMs}` | 重建每批提交后 | 状态栏 |
| `EVT-index.state` | `index.state` | `{state, noteCount}` | 状态迁移 | 全局 |
| `EVT-sync.state` | `sync.state` | `{state, pending, conflicts, lastError, authRequired}` | 状态迁移 | 状态栏、设置页 |
| `EVT-conflict.detected` | `conflict.detected` | `{paths:[]}` | 同步产生冲突副本后 | 通知中心 |
| `EVT-error.raised` | `error.raised` | `{code, message, detail}` | 后台任务失败（无对应请求） | 通知中心 |

> 事件共 7 个。表中「文档标识」用于本文档内部交叉引用（如 §4 流程图、§10.2 异常映射），「线上事件名」是 `EVT-x` 中 `x` 的字面值，二者一一对应。

**事件与命令的边界**：命令用于「用户发起、需要应答」的操作；事件用于「后台发生、需要通知」的状态变化。同一状态变化不得既有命令应答又有事件重复推送（例如保存成功只回命令应答，不再发 `EVT-note.changed`；`EVT-note.changed` 专用于非本窗口发起的变更）。

### 5.5.1 `NoteStore`

### 5.5.5 其他端口

| 端口 | 方法 | 说明 |
|---|---|---|
| `Watcher` | `start(cb)`, `stop()`, `overflowed() -> bool` | 事件回调只允许入队，不允许做 I/O |
| `CredentialStore` | `set(ref, secret)`, `get(ref) -> Option<Secret>`, `delete(ref)` | `secretRef` 是不透明字符串，永不落盘明文 |

### 5.5.6 应用层服务接口

> 5.5.1–5.5.5 是**基础设施端口**（由 L4 实现、L2 调用）；本节是**应用层服务接口**（由 L2 实现、L1 经 IPC 调用）。两者层次不同，命名不得混用——这是 v1.1 修正 `Searcher` 与 `IndexStore::search` 重名的方式。

| 服务接口 | 方法 | 说明 |
|---|---|---|
| `NoteService` | `create / read / save / delete / restore / rename` | 用例编排，返回 `NoteContent` 或 `WriteOutcome` |
| `SearchService` | `search(q: SearchQuery) -> SearchPage` | 查询路由、排序、片段；内部调用 `IndexStore::search`（§5.5.2） |
| `LinkService` | `backlinks / mentions / graph / resolve / propagate_rename` | 链接解析与重命名联动 |
| `SyncService` | `configure / run / status` | 同步状态机（§3.5） |
| `BackupService` | `create / verify / restore` | 备份与恢复 |
| `ExportService` | `export(p: ExportParams) -> ExportResult` | 导出与缺失资源报告 |

**契约**：服务层不直接触碰文件系统或 SQLite，全部经 5.5.1–5.5.5 的端口；服务层只负责用例编排与事务边界。例如 `NoteService::save` 内部依次调用 `NoteStore::write_atomic`（落盘）与 `IndexQueue::enqueue`（异步索引），**顺序不可交换**——约束见 §4 的「时序图：F-03 保存与 F-08 同步」中时序图一后附的时序约束段。

## 5.6 外部接口

### 5.6.1 文件系统

| 操作 | 约束 |
|---|---|
| 读取 | 单篇 ≤ 10 MB（CON-06）；超过按 EX-10 只读打开 |
| 写入 | 原子：临时文件（同目录，`.<name>.tmp-<rand>`）→ `fsync` → `rename` → 目录 `fsync` |
| 监听 | Windows 用 `ReadDirectoryChangesW`；macOS 用 FSEvents；Linux 用 inotify。**失败或溢出时按 EX-14 降级为轮询（默认 300 s，可配置）** |
| 路径 | 统一为 `/` 分隔的库相对路径；进入 `PathValidator` 前先 NFKC 归一化 |

### 5.6.2 SQLite

| 项 | 值 |
|---|---|
| 引擎 | SQLite（FTS5 必须启用） |
| 连接 | 写连接 1 个（独占，`index-worker` 持有）；读连接池 2 个 |
| 日志模式 | WAL |
| 同步级别 | `NORMAL`（写入路径另有原子文件保证，不依赖 DB 的 `FULL`） |
| 忙等待 | `busy_timeout = 5000 ms` |
| 页缓存 | 64 MB |
| 迁移 | `meta.schema_version` 递增；不匹配则重建而非就地迁移（索引是缓存，BR-05） |

### 5.6.3 WebDAV

| 项 | 值 |
|---|---|
| 方法 | `PROPFIND`（Depth:1）、`GET`、`PUT`、`DELETE`、`MKCOL` |
| 认证 | HTTP Basic（凭据存 OS 凭据库）或 Digest；由服务端 `WWW-Authenticate` 决定 |
| 条件请求 | 上传带 `If-Match: <etag>`；返回 412 视为「远端已变」，不覆盖 |
| 超时 | 连接 10 s，请求 30 s |
| 重试 | 网络类错误退避 1/2/4/8/16 s，最多 5 次（TR-06）；401/403 不重试 |
| 并发 | 单任务串行上传；单文件最大 100 MB |

### 5.6.4 平台 WebView（PDF 导出）

| 平台 | 能力 | 状态 |
|---|---|---|
| Windows | WebView2 `PrintToPdfAsync`（官方文档确认；同一时刻仅允许一个打印任务，目标为绝对路径且会覆盖同名文件） | 采用 |
| macOS | `WKWebView` 的 PDF 生成能力 | M2 验证 |
| Linux | WebKitGTK 的打印到 PDF | M2 验证 |

## 5.7 调用限制汇总

| 项 | 限制 | 理由 |
|---|---|---|
| 单次检索返回 | ≤ 50 条/页，`nextCursor` 分页 | 首屏延迟预算（NFR-PER-01） |
| 短查询扫描 | 硬上限 1 s，超时返回部分结果 + `degraded` | NFR-PER-01 |
| 索引写批 | ≤ 200 篇/事务 | 控制 WAL 增长与提交延迟 |
| 索引写并发 | 1（单写者） | SQLite + FTS5 写放大 |
| 同步任务 | 1（`E_SYNC_BUSY`） | 避免同一文件并发写 |
| 备份并发 | 1；备份/恢复期间 `index-worker` 暂停 | 保证文件与索引一致 |
| 单篇文件 | ≤ 10 MB（CON-06） | EX-10 |
| 库规模 | ≤ 20 万篇（CON-05） | 分两档：≤10 万篇按基线指标承诺；10–20 万篇进入「大库模式」，目标长查询 ≤100 ms、短查询 ≤2 s。档位定义与界面提示见 §6.9 规模档位表，验证节点见 §11.4 `VT-PER-07` |
| 预览渲染 | 防抖 150 ms，同笔记请求去重 | NFR-PER-03 |

| 检查项 | 结论 |
|---|---|
| 命令字段 ↔ 数据模型字段 | `contentHash` / `mtimeMs` / `sizeBytes` / `hasAttachment` 与 §6.4 `notes` 一致 |

# 6. 数据设计

## 6.1 数据分类与权威性

| 类别 | 存放位置 | 是否权威 | 丢失后果 |
|---|---|---|---|
| 笔记正文与元数据 | 库目录 `*.md` | **权威（BR-01）** | 不可恢复，须备份 |
| 附件 | 库目录 `attachments/` | **权威** | 同上 |
| 回收站内容 | 库目录 `trash/` | **权威**（用户资产） | 保留期内可恢复；超期由 TR-05 清理 |
| 索引 | 应用数据 `index.db` | 派生 | 自动重建（BR-05） |
| 草稿 | 应用数据 `drafts/` | 临时 | 最多丢 500 ms 输入 |
| 版本快照 | 应用数据 `snapshots/` | 派生（有保留期） | 丢失历史版本 |
| 同步状态 | `index.db` 内 `sync_state` / `sync_tombstone` | 派生 | 退化为全量比对，可能误判删除 |
| 配置 | 应用数据 `settings.json` | 权威（小） | 需重新配置 |
| 凭据 | OS 凭据库 | 权威（小） | 需重新授权 |

**唯一性约定**：`vault_id = sha256(规范化绝对路径)[:16]`，用于隔离不同库的索引与草稿。

## 6.2 目录布局

```
<vault>/                                  ← 用户可见、可备份、可迁移
├── 课程/数据结构/二叉搜索树.md
├── 文献/...
├── attachments/
│   └── 20260928-143000-diagram.png
└── trash/                                ← 库内回收站（FR-EDT-07）
    └── 课程/数据结构/二叉搜索树 (deleted 20261017-143000).md

<app-data>/NoteBase/                      ← 应用私有，不进入备份与同步
├── settings.json
├── vaults/<vault_id>/
│   ├── index.db  (+ -wal, -shm)
│   ├── drafts/<sha256(path)[:16]>.json
│   ├── snapshots/<yyyy>/<mm>/<hash16>.md
│   └── logs/app-<yyyyMMdd>.log
└── backups/                              ← 默认备份目录（库外，FR-BAK-01）
```

**回收站设计（FR-EDT-07、BR-07）**：`trash/` 内部**镜像原目录结构**，文件名追加 ` (deleted YYYYMMDD-HHmmss)` 后缀。恢复时去掉后缀即得原路径，**不需要任何额外的元数据文件**——这是为了让「删除」只产生一次文件移动，不产生需要单独维护的索引，避免回收站自身成为不一致源。

| 项 | 规则 |
|---|---|
| 索引 | `trash/` 整体排除，不建索引（被删笔记不应出现在检索结果中） |
| 同步 | 默认排除（`excludeGlobs` 内置 `trash/**`），避免删除动作被传播为远端的「移动」 |
| 备份 | **包含**（`trash/` 属于用户资产），但恢复时不覆盖同名现行文件 |
| 清理 | 按 TR-05 每 24 h 扫描后缀时间戳，超过保留期的文件物理删除并记日志 |

## 6.3 笔记文件格式

正文与 frontmatter 严格遵循需求文档 §8.1 / §8.2：

- UTF-8 无 BOM 写入；读取容忍 BOM 与非法字节（FR-EDT-10）。
- 新建文件用 LF；保存保留原换行风格。
- frontmatter 字段：`title`、`tags`、`aliases`、`created`、`updated`、`favorite`、`status`。
- frontmatter 解析失败时，整篇按正文处理，属性面板报错，**保存不得重写该段**（§8.2、EX-18）。

## 6.4 `index.db` 模式

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;

-- 元信息
CREATE TABLE meta (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
-- schema_version / tokenizer_version / vault_id / last_reconcile_ms / rebuild_cursor

-- 笔记主表（路径即身份，见 D-02）
CREATE TABLE notes (
  path           TEXT PRIMARY KEY,                       -- 库相对路径，'/' 分隔，NFC
  title          TEXT NOT NULL,
  size_bytes     INTEGER NOT NULL CHECK (size_bytes >= 0),
  mtime_ms       INTEGER NOT NULL CHECK (mtime_ms >= 0),
  content_hash   TEXT NOT NULL,                          -- sha256 hex，64 字符
  created_ms     INTEGER,
  updated_ms     INTEGER,
  has_attachment INTEGER NOT NULL DEFAULT 0 CHECK (has_attachment IN (0, 1)),
  indexed_at_ms  INTEGER NOT NULL
);
CREATE INDEX idx_notes_mtime ON notes(mtime_ms);

-- 别名（供 [[别名]] 解析与检索）
CREATE TABLE aliases (
  note_path TEXT NOT NULL REFERENCES notes(path) ON DELETE CASCADE,
  alias     TEXT NOT NULL,
  PRIMARY KEY (note_path, alias)
);
CREATE INDEX idx_aliases_alias ON aliases(alias);

-- 标签（层级标签以 '/' 原样存储，聚合查询在应用层展开）
CREATE TABLE tags (
  note_path TEXT NOT NULL REFERENCES notes(path) ON DELETE CASCADE,
  tag       TEXT NOT NULL,
  PRIMARY KEY (note_path, tag)
);
CREATE INDEX idx_tags_tag ON tags(tag);

-- 链接（派生自正文，随索引重建）
CREATE TABLE links (
  id          INTEGER PRIMARY KEY,
  source_path TEXT NOT NULL REFERENCES notes(path) ON DELETE CASCADE,
  target_text TEXT NOT NULL,
  target_path TEXT REFERENCES notes(path) ON DELETE SET NULL,
  line        INTEGER NOT NULL CHECK (line >= 1),
  col         INTEGER NOT NULL CHECK (col >= 1),
  resolved    INTEGER NOT NULL CHECK (resolved IN (0, 1)),
  ambiguous   INTEGER NOT NULL DEFAULT 0 CHECK (ambiguous IN (0, 1))
);
CREATE INDEX idx_links_source ON links(source_path);
CREATE INDEX idx_links_target ON links(target_path);

-- 全文索引（trigram：只服务 ≥3 字符查询，见 D-03）
-- 表形态：普通 FTS5 表（非 external content、非 contentless）。
-- 它自带一份 title/body 副本，影子表名为 note_fts_content；
-- 短查询（<3 字符）的正文 LIKE 扫描直接作用于该影子表，不读 notes 表。
CREATE VIRTUAL TABLE note_fts USING fts5(
  path UNINDEXED,
  title,
  body,
  tokenize = 'trigram'
);

-- 版本快照索引（blob 在文件系统）
CREATE TABLE snapshot_index (
  note_path  TEXT NOT NULL,
  version_id TEXT NOT NULL,          -- 内容 sha256 前 16 位
  blob_rel   TEXT NOT NULL,
  size_bytes INTEGER NOT NULL,
  created_ms INTEGER NOT NULL,
  PRIMARY KEY (note_path, version_id)
);
CREATE INDEX idx_snapshot_age ON snapshot_index(created_ms);

-- 同步状态（base_hash 是三方比对的基准）
CREATE TABLE sync_state (
  path           TEXT PRIMARY KEY,
  base_hash      TEXT,
  local_hash     TEXT,
  remote_etag    TEXT,
  device_id      TEXT NOT NULL,
  last_synced_ms INTEGER,
  state          TEXT NOT NULL CHECK (state IN ('clean','dirty','pending','conflict'))
);

-- 删除墓碑（区分「本地删除」与「从未同步」）
CREATE TABLE sync_tombstone (
  path       TEXT PRIMARY KEY,
  deleted_ms INTEGER NOT NULL,
  base_hash  TEXT
);

-- 重命名日志（幂等续跑）
CREATE TABLE rename_journal (
  id           INTEGER PRIMARY KEY,
  from_path    TEXT NOT NULL,
  to_path      TEXT NOT NULL,
  affected     TEXT NOT NULL,        -- JSON 数组
  done         TEXT NOT NULL,        -- JSON 数组
  created_ms   INTEGER NOT NULL,
  state        TEXT NOT NULL CHECK (state IN ('running','done','failed'))
);
```

**关键约束说明**：

1. `notes.path` 为主键，即**路径就是笔记身份**（D-02）。因此重命名是「删旧行 + 插新行 + 改引用」，不是改一个 ID 字段。
2. `links.target_path` 为 `NULL` 表示未解析；外键 `ON DELETE SET NULL` 只处理目标被删的情况，`resolved` 字段需由 `link-svc` 在同一事务内一并置 0。
3. `note_fts` 与 `notes` 必须同事务更新——`index-store` 提供 `upsert_note_tx()` 唯一入口，禁止绕过。
4. 所有时间字段为 Unix 毫秒（UTC），frontmatter 中的 `created/updated` 另行按 ISO 8601 带时区偏移序列化（TR-08）。
5. `meta.schema_version` 与 `meta.tokenizer_version` 任一不匹配即触发重建（BR-05）。
6. **`note_fts` 是普通 FTS5 表，自带正文副本**，因此 `notes` 与 `note_fts` 各存一份正文。这不是冗余失误：影子表 `note_fts_content` 是短查询 `LIKE` 扫描的唯一扫读对象，避免回表到 `notes`（`notes` 只存元数据，不存正文）。该副本约等于语料体积，已计入 §6.9 的 2.48× 中。

## 6.5 草稿文件格式

`drafts/<sha256(path)[:16]>.json`：

```json
{
  "path": "课程/数据结构/二叉搜索树.md",
  "body": "# ...",
  "baseHash": "sha256:9f2c...",
  "savedAtMs": 1760000001234,
  "clientSeq": 42
}
```

**写入策略**：编辑过程中每 500 ms 覆盖写（原子替换），正常保存成功后删除。文件很小（仅当前编辑的一篇），不构成 I/O 压力。

## 6.6 快照与备份

**快照（版本历史）**：内容哈希变化时写入 `snapshots/<yyyy>/<mm>/<hash16>.md`，同一哈希只存一份（天然去重）。`snapshot_index` 记录映射。清理任务按 TR-04 删除超过 30 天的记录与 blob。

**备份包**：遵循需求文档 §8.4：

```
backup-20261017-120000.zip
├── manifest.json      { formatVersion, createdAt, noteCount, attachmentCount, checksum }
├── notes/             保留库内相对路径
└── attachments/
```

`checksum` 定义为「按路径排序后，逐文件 `sha256(path + '\0' + content)` 的哈希再拼接取 sha256」，可在解压前校验完整性，也可在恢复后重算比对。

## 6.8 一致性与恢复策略

| 一致性目标 | 手段 | 失败时的恢复 |
|---|---|---|
| 文件写入原子性 | 临时文件 + fsync + rename | 临时文件残留由启动清理任务删除 |
| 索引与文件一致 | 事件驱动增量 + 定期对账 | 对账发现的差异直接重索引该文件 |
| 索引内部一致（notes ↔ fts） | 单事务写入 | 启动时校验行数偏差 > 1% 则全量重建 |
| 快照与正文一致 | 以内容哈希为键，先写 blob 再写索引行 | 孤儿 blob 由清理任务回收 |
| 同步三方一致 | `base_hash` 为基准 | base 缺失时全部差异判冲突（保守） |
| 崩溃后索引可恢复 | WAL + 重建 | 无法打开则删库重建（BR-05） |

**定期对账**：`watcher` 的轮询降级路径同时承担对账职责——每 300 s 遍历一次库目录，比较 `(mtime, size)` 与 `notes` 表，差异入队重索引。这是 EX-14「事件丢失」的兜底，也是网络盘场景的唯一正确性保证。

**索引行数校验**：`note_fts` 行数与 `notes` 行数偏差超过 1% 视为不一致（FTS 行与主表脱节通常意味着事务被绕过），触发重建。

## 6.9 容量规划（基于实测）

| 规模 | 语料 | 索引体积（×2.48） | 单次重建（实测外推） | 短查询扫描 |
|---|---|---|---|---|
| 1 万篇 | ~51 MB | ~127 MB | ~2.8 min | ~70 ms |
| 10 万篇 | ~515 MB | ~1.28 GB | **28.3 min（实测）** | **670–742 ms（实测）** |
| 20 万篇（CON-05 上限） | ~1.03 GB | ~2.55 GB | ~57 min | ~1.4 s（外推） |

**索引体积拆解（10 万篇）**：1276.7 MB 中约 **515 MB** 是 `note_fts` 自带的正文副本（§6.4 约束 6），约 **762 MB** 是 trigram 倒排结构（含位置信息）。前者随语料线性增长，后者约为正文的 1.48 倍。这也解释了为什么 NFR-PER-06 的 3 倍上限不能简单理解为「倒排结构占 3 倍」——其中有一倍是正文副本。

**规模档位与降级目标**（v1.1 新增）

| 档位 | 库规模 | 长查询（≥3 字）首屏 P95 | 短查询（<3 字）首屏 P95 | 界面行为 |
|---|---|---|---|---|
| 基线档 | ≤ 10 万篇 | ≤ 50 ms | ≤ 1 s | 正常 |
| **大库档** | **10–20 万篇** | **≤ 100 ms** | **≤ 2 s** | 状态栏显示「大库模式」；进入时提示检索可能较慢 |
| 超限 | > 20 万篇（CON-05） | 不承诺 | 不承诺 | 启动时提示超出设计规模，功能仍可用 |

> 大库档的两个数字是**设计目标**而非实测值：短查询扫描成本与库规模近似线性（10 万篇实测 670–742 ms，外推 20 万篇约 1.4 s），取 2 s 作为含余量的目标，须在原型阶段以 20 万篇语料实测确认。这样处理是因为 NFR-PER-01 的指标原文限定在「10 万篇、约 500 MB」，超出该范围的承诺不应凭空给出。

## 6.10 数据字典（关键字段）

| 表.字段 | 类型 | 约束 | 含义 | 来源 |
|---|---|---|---|---|
| `notes.path` | TEXT | PK，非空，NFC，`/` 分隔 | 库相对路径 | 文件系统 |
| `notes.title` | TEXT | 非空 | 显示标题：frontmatter `title` 优先，否则文件名去扩展名 | 文件内容 |

## 7.4 交互规则

1. **不阻塞输入**：任何后台任务（索引、同步、导出）都在后台执行，界面只显示状态，不弹模态框。
2. **破坏性操作二次确认**：彻底删除、恢复备份、重命名批量改写均需确认，并展示影响清单（FR-LNK-04）。
3. **错误可区分**：空结果、降级结果、不可服务三种状态在视觉上必须不同（EX-21 的界面侧要求）。
4. **键盘可达**：新建、检索、切换、保存四项均有快捷键（NFR-USA-02）；命令面板可完成全部命令（U3）。
5. **焦点保留**：任何后台事件引起的界面刷新不得抢走编辑器焦点。
6. **图谱视图为只读消费方**：关系图谱（FR-LNK-05，低优先级）通过 `CMD-link_graph` 读取 `links` 的图结构，不参与编辑流程，也不持有自己的缓存；`maxNodes` 默认 500，超过时提示「仅展示邻域」而不是渲染全库——全库 10 万节点的力导向布局在浏览器端不可行。

## 7.5 可访问性

- 深色/浅色两套语义色板，正文对比度 ≥4.5:1，大号文本 ≥3:1（NFR-USA-03）。
- 全部交互元素可 Tab 到达，焦点环可见。
- 编辑器支持系统级缩放；行宽可配置。

# 8. 非功能设计

## 8.1 性能

| 需求 | 目标 | 设计措施 | 验证 |
|---|---|---|---|
| NFR-PER-01 | 长查询首屏 P95 ≤50 ms；短查询 ≤1 s（≤10 万篇基线档；10–20 万篇按 §6.9 大库档 ≤100 ms / ≤2 s） | trigram 倒排 + 短查询双阶段（标题快路径先返回）；结果分页 50 | 复用 10 万篇基准语料，`bench.py` 同法测量；大库档另需 20 万篇语料实测 |
| NFR-PER-02 | 索引加载 ≤2 s；完整冷启动 ≤2 s | 首屏不等待索引；只读打开 + 惰性预热；窗口骨架先呈现 | 冷启动计时（清文件缓存，10 次取中位数） |
| NFR-PER-03 | 输入延迟 P95 ≤50 ms | 编辑与渲染解耦：输入在主线程，预览 150 ms 防抖后送 render-pool；CodeMirror 视口虚拟化只渲染可见行 | 输入事件处理耗时采样；1 MB 文档实测 |
| NFR-PER-04 | 全量重建 ≤30 min | 分块事务（200 篇/批）+ 临时库原子替换 + 断点续建 | 实测 28.3 min；重建期间应用可用 |
| NFR-PER-05 | 内存 ≤1 GB | WebView 独立进程；SQLite 页缓存 64 MB；索引不整载入内存（走 mmap/页缓存）；标签页惰性销毁 | 任务管理器采样「常规使用」序列 |
| NFR-PER-06 | 索引 ≤3× 语料 | trigram 实测 2.48×；定期 `VACUUM`；不建第二套索引 | 索引文件大小 / 语料大小 |

**性能设计的三条硬约束**（会体现在代码结构里）：

1. **索引永不整载入内存**。查询只走 SQLite 的页缓存，这样 100 万篇的库也不会因索引膨胀导致 OOM。
2. **UI 线程不做 I/O**。任何超过 5 ms 的操作（文件读、索引查、渲染）都必须异步；这也是 F-01 首屏不等待索引的原因。
3. **分页而非全量**。检索一次最多 50 条，翻页用游标，避免大结果集序列化。

**风险**：

| 编号 | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R-01 | 库规模达到 CON-05 上限 20 万篇时，短查询扫描外推约 1.4 s，超出基线档的 1 s | 短查询体验下降 | **已量化降级**：10–20 万篇进入「大库模式」，目标 P95 ≤2 s 并在界面提示（§6.9）；后续可引入二元组索引（D-03 的备选 B）彻底解决 |
| R-02 | 全量重建 28.3 min 距 30 min 预算仅剩 6% | 硬件较差时可能超预算 | 断点续建 + 后台执行；预算按 10 万篇标定 |
| R-03 | WebView 前端渲染 1 MB 文档时可能卡顿 | NFR-PER-03 | CodeMirror 视口虚拟化 + 关闭实时预览（FR-EDT-09 的降级区间） |

## 8.2 可靠性

| 需求 | 设计措施 | 验证 |
|---|---|---|
| NFR-REL-01 崩溃零丢失 | 500 ms 草稿落盘；保存判定表；启动扫描草稿 | 进程随机终止 200 次，统计内容丢失 |
| NFR-REL-02 无半写文件 | 临时文件 + fsync + rename + 目录 fsync | 写盘中途杀进程，逐一解析 |
| NFR-REL-03 备份可还原 | 纯 zip + 明文 Markdown，不依赖应用 | 干净机器解压抽查 |
| BR-02 绝不覆盖 | `create_new` 语义 + 序号后缀重试 | 同名创建用例 |
| BR-05 索引可丢弃 | 索引为独立文件，删除即重建 | 删除 index.db 后启动 |

**故障域划分**：文件系统故障不影响索引（索引可重建）；索引故障不影响数据（BR-01）；同步故障不影响本地（FR-SYN-03）。三者互相隔离，任一失败都不应导致应用不可用。

## 8.3 安全

| 需求 | 设计措施 |
|---|---|
| NFR-SEC-01 不外发内容 | 无遥测、无崩溃上报；唯一的网络出口是 `webdav-sync`，且仅在用户配置后启用；日志脱敏（不写正文） |
| NFR-SEC-02 凭据不落盘明文 | `CredentialStore` 端口 → OS 凭据库；`settings.json` 只存 `credentialRef` |
| 渲染安全 | comrak 默认安全转义 + tagfilter；预览在沙箱 WebView 中渲染，禁用脚本 |
| 路径穿越 | 所有路径先经 `PathValidator`：必须位于库内、拒绝 `..`、拒绝符号链接指向库外 |
| 文件锁定竞争 | `WriteGuard` 按路径加锁，避免并发写 |

**威胁模型（简化）**：本地单用户桌面应用，主要威胁是「笔记内容中的恶意 HTML」与「同步凭据泄露」。前者由 tagfilter + 沙箱处理，后者由 OS 凭据库处理。不存在多租户与远程攻击面。

## 8.4 可扩展性

| 扩展点 | 预留方式 | 不做的原因 |
|---|---|---|
| 同步后端 | `SyncBackend` 端口，V1 只实现 WebDAV | Git 后端需要处理工作区脏状态与合并语义，V1 不做（FR-SYN-01 的「或」已由 WebDAV 满足） |
| 导出格式 | `Exporter` 端口 | 新增格式只加实现，不改流程 |
| 检索策略 | `QueryRouter` 可替换 | 后续引入二元组索引时只改路由层 |
| 界面布局 | `layoutPreset` 配置驱动 | 新增角色画像只需加预设 |
| 插件 | **不做**（OUT-04） | 插件沙箱与 API 稳定性超出单人范围；数据层已有 frontmatter 自定义字段作为轻量扩展点 |

## 8.5 可维护性

| 措施 | 说明 |
|---|---|
| 分层依赖规则 | §2.1 的 R1–R5，可在 CI 中用依赖检查工具机械校验 |

# 9. 设计决策与权衡

> 每个决策记录：背景、备选方案、评估、决定、影响。评估尽量引用实测数据（需求文档附录 B）。

## D-01 桌面运行时：Tauri vs Electron vs 原生

| 备选 | 优势 | 劣势 |
|---|---|---|
| **Tauri 2**（选定） | 二进制小；内存与冷启动接近原生；Rust 适合文件与索引处理；系统 WebView 复用 | 三平台 WebView 行为有差异；需要 Rust |
| Electron | 渲染一致；生态成熟 | 常驻内存高（空闲即数百 MB）；冷启动慢；安装包大 |
| 原生三套 UI | 性能最好 | 三套 UI 工作量，单人不可行 |

**决定**：Tauri。**理由**：NFR-PER-05（≤1 GB）与 NFR-PER-02（≤2 s）对内存与启动敏感，Electron 的空载基线会吃掉大部分预算。**代价**：WebView 差异带来的渲染一致性风险，缓解方式是限制 CSS 特性基线 + 三平台截图回归。**影响**：NFR-CMP-01 的实现成本上升。

## D-02 笔记身份：路径 vs UUID vs 内容哈希

| 备选 | 优势 | 劣势 |
|---|---|---|
| **库相对路径**（选定） | 与文件系统一致；无隐藏字段；外部工具友好；BR-01 的直接推论 | 重命名要改引用（F-07）；大小写与 Unicode 归一化需统一 |
| frontmatter 内 UUID | 重命名零成本 | 污染用户文件；外部工具新建的笔记无 UUID；与 BR-03「开放格式」气质不符 |
| 内容哈希 | 天然去重 | 任何编辑都改变身份，不可用 |

**决定**：路径。**理由**：本地优先的核心是「文件即数据源」，身份若藏在 frontmatter 里，就出现了「文件内容决定文件身份」的循环依赖；外部创建的文件也需要应用写一次 UUID 才能纳管，违反 FR-IO-03「直接打开已有库」。**代价**：重命名是重量级操作，必须做事务化与幂等续跑（F-07）。**影响**：`rename_journal` 表、`planOnly` 预演接口、`E_PARTIAL_RENAME` 错误码。

## D-03 中文检索索引：trigram vs unicode61 vs 二元组 vs Tantivy

| 备选 | 召回（实测） | 首屏时延（实测） | 建库（实测） | 体积（实测） | 结论 |
|---|---|---|---|---|---|
| **FTS5 trigram**（选定为主） | ≥3 字 100%；<3 字 0% | 0.1–0.9 ms | 28.3 min | 2.48× | 采用，短查询另走扫描 |
| FTS5 unicode61 | 四字 4.5%；其余 0% | 0.1–1.1 ms | 41.3 s | 1.19× | **否决**：正确性不成立 |
| 自建二元组索引 | 预期 ≥2 字 100% | 未测 | 未测 | 预计与 trigram 同级 | **推迟**：能解决 2 字查询，但需独立实测；V1 用扫描已满足 NFR-PER-01 |
| Tantivy + ngram | 理论可覆盖 1–3 字 | 未测 | 未测 | 未测 | **否决**：引入第二套索引框架，与 SQLite 事务边界难统一，复杂度超出单人规模 |

**决定**：trigram 主索引 + 短查询双阶段扫描。**理由**：实测数据支持，且短查询扫描实测 670–742 ms 已在 NFR-PER-01 的 1 s 预算内；引入第二套索引会让数据设计与一致性策略复杂度翻倍。**代价**：2 字查询体验一般（约 0.7 s）。**影响**：FR-SRC-05 的三项条件、EX-21、NFR-PER-01 的分段指标、§6.9 的 20 万篇风险。

> 若后续要优化 2 字查询，替换点被限制在 `QueryRouter` 一处（§8.4），不需要改流程与接口。

## D-04 索引定位：派生缓存 vs 主存储

| 备选 | 结论 |
|---|---|
| **派生缓存**（选定） | 与 BR-01/BR-05 一致；索引可删、可重建；数据安全只依赖文件 |
| 主存储（索引内含正文） | 否决：违反「文件即数据源」，且一旦索引损坏就丢数据 |

**决定**：派生缓存。**影响**：所有查询都必须能容忍索引缺失（降级为扫描），这也是 F-01 与 EX-05 的设计来源。

## D-05 索引存放位置：应用数据目录 vs 库内 `.notebase/`

| 备选 | 优势 | 劣势 |
|---|---|---|
| **应用数据目录**（选定） | 库目录干净（BR-03）；索引不进备份与同步（FR-BAK-01、FR-SYN-05） | 库迁移后需重建（28.3 min） |
| 库内 `.notebase/` | 库自包含，迁移即用 | 污染用户目录；会被同步与备份带上；`.notebase` 内部路径与 `index.db` 的 WAL 文件在同步时极易冲突 |

**决定**：应用数据目录。**理由**：索引 1.28 GB、含 WAL 文件，放进库目录会让同步与备份变得不可控；而「迁移后重建」的成本可接受，因为迁移是低频操作且重建在后台进行。**影响**：EX-08 的重新定位向导、`vault_id` 机制。

## D-06 编辑器内核：CodeMirror 6 vs WYSIWYG vs contenteditable

| 备选 | 优势 | 劣势 |
|---|---|---|
| **CodeMirror 6**（选定） | 视口虚拟化适配大文档；增量解析；Markdown 模式成熟；可访问性好 | 需要自行拼接 Markdown 扩展行为 |
| ProseMirror（WYSIWYG） | 所见即所得 | Markdown 往返有损：清单外语法的内容会被改写，违反 EX-19「保留原文」 |
| 原生 contenteditable | 无依赖 | 大文档性能与 IME 行为难以控制 |

**决定**：CodeMirror 6。**理由**：EX-19 要求「清单外语法原样保留」，WYSIWYG 模型无法保证无损往返；而 NFR-PER-03 要求 1 MB 文档可用，必须依赖视口虚拟化。**影响**：预览需要独立渲染路径（D-07）。

## D-07 渲染：单一 Rust 解析器 vs 前端解析 vs 双解析器

| 备选 | 优势 | 劣势 |
|---|---|---|
| **单一 Rust 解析器（comrak）**（选定） | 预览、导出、索引抽取共用一套语义，NFR-CMP-02 天然成立 | 每次预览要过一次 IPC（150 ms 防抖后可接受） |
| 前端 JS 解析器 | 预览零延迟 | 与导出用的解析器不一致，容易出现「预览对、导出错」 |
| 双解析器 | 各自最优 | 两套语义必然分叉，验收无法一致 |

**决定**：comrak 单解析器。**已核实的能力**：comrak 是「100% CommonMark 兼容的 GFM 解析器」，支持表格、任务列表、删除线、自动链接、tagfilter 全部 5 项扩展。**配置约束**：脚注、定义列表、上标必须关闭（附录 A §A.5）。**影响**：预览延迟增加一次 IPC；索引抽取与导出复用同一解析结果。

## D-08 同步模型：文件级三方比对 vs CRDT vs Git merge

| 备选 | 优势 | 劣势 |
|---|---|---|
| **文件级三方比对**（选定） | 与「文件即单元」一致；实现可控；冲突可解释 | 无字符级合并 |
| CRDT（字符级） | 自动合并 | 需要私有元数据与持久化状态，破坏纯文本可移植性；实现复杂度高 |
| Git merge | 复用成熟合并 | 需要工作区干净、冲突标记会写进文件、用户要懂 Git |

**决定**：文件级三方比对。**理由**：BR-06 已明确 V1 不做字符级合并；CRDT 的元数据会破坏「任何编辑器都能读写这些文件」（BR-03）。**影响**：`sync_state.base_hash`、`sync_tombstone`、冲突副本命名（TR-07）。

## D-09 冲突处理：保留双份 vs 自动合并

已在 BR-06 中锁定。设计补充：冲突时**本地保持原名、远端内容另存副本**，而不是反过来。**理由**：本地是用户正在看的版本，改它的名字会造成「刚才编辑的文件不见了」的错觉；副本的命名带时间戳与设备标识，用户可自行判断。

## D-10 PDF 导出：平台打印 vs 自建排版

| 备选 | 优势 | 劣势 |
|---|---|---|
| **平台 WebView 打印**（选定） | 与预览同源，格式一致；无额外排版引擎 | 三平台能力不一致；需验证 |
| 自建 PDF 库排版 | 跨平台一致 | 中文字体、分页、表格、代码高亮的排版工程量巨大，单人不可行 |

**决定**：平台打印，**并明确接受分平台差异**。Windows 侧已核实 WebView2 提供 `PrintToPdfAsync`（同一时刻仅一个任务、目标为绝对路径、覆盖同名文件）。macOS/Linux 在 M2 验证；不可用时降级为 HTML 导出（`E_PDF_UNSUPPORTED`）。**影响**：FR-IO-01 的验收需按平台分别执行。

## D-11 索引一致性：事件驱动 vs 全量轮询 vs 混合

| 备选 | 优势 | 劣势 |
|---|---|---|
| **混合**（选定） | 事件驱动保证低延迟（TR-02）；轮询对账兜住事件丢失（EX-14） | 两套路径都要实现 |
| 仅事件驱动 | 延迟最低 | 网络盘/事件溢出时永久不一致 |
| 仅轮询 | 简单 | 无法满足 1 s 增量时延 |

**决定**：事件驱动 + 300 s 对账。**理由**：Microsoft 官方文档明确变更通知在网络目录上有两种失败机制（不支持时函数失败、缓冲区溢出丢弃全部变更），仅靠事件无法保证正确性。**影响**：`watcher` 的轮询降级路径、`meta.last_reconcile_ms`。

## D-12 索引存放在 SQLite vs 内存 vs 专用搜索服务

| 备选 | 结论 |
|---|---|
| **SQLite（FTS5）**（选定） | 单文件、事务、WAL、可嵌入；实测满足指标 |
| 进程内内存索引 | 否决：20 万篇时内存不可控（NFR-PER-05） |
| 独立搜索服务 | 否决：违反「无服务端」（OUT-03） |

# 10. 异常与故障处理设计

## 10.1 故障模式目录

按故障域分四类，每类给出检测点、处理与恢复：

| 域 | 故障模式 | 检测点 | 处理 | 恢复 |
|---|---|---|---|---|
| 存储 | 磁盘满、无权限、文件被占用 | 写入返回错误 | 停写 + 提示 | 用户腾出空间后重试 |
| 存储 | 外部修改、外部删除 | 哈希/存在性比对 | 三选项 / 重建提示 | 用户选择 |
| 索引 | 损坏、schema 不匹配、行数偏差 | 打开失败 / 版本比对 / 行数校验 | 自动重建 | 重建完成 |
| 索引 | 事件丢失、缓冲区溢出 | watcher 溢出标志 / 对账差异 | 全量对账 | 差异文件重索引 |
| 同步 | 网络不可达、凭据失效、412 抢占 | HTTP 状态 | 退避 / 转授权 / 回退 | 重试或重新比对 |
| 同步 | 双端同改 | 三方比对 | 保留双份 | 用户合并 |
| 运行 | 崩溃、断电 | 启动时草稿存在 | 恢复向导 | 用户确认 |
| 环境 | 库目录丢失、网络盘断连 | 启动校验 / 读失败计数 | 重定位向导 / 只读降级 | 恢复连接后重建 |

## 10.2 EX-01 ~ EX-22 的设计映射

| EX | 故障 | 检测模块 | 接口/错误码 | 恢复动作 | 界面侧 |
|---|---|---|---|---|---|
| EX-01 | 磁盘满/无权限 | `fs-store` | `E_IO_DISK_FULL` / `E_IO_PERMISSION` | 停自动保存，保留内存内容 | 顶部条 + 另存入口 |

## 10.3 恢复策略分级

| 级别 | 策略 | 适用 | 用户感知 |
|---|---|---|---|
| L1 自动重试 | 退避重试（TR-06） | 瞬时故障（占用、网络） | 无感，仅状态栏 |
| L2 自动重建 | 索引删除重建（BR-05） | 索引损坏、版本不匹配 | 进度条 |
| L3 降级可用 | 只读模式、扫描替代索引、HTML 替代 PDF | 能力缺失 | 顶部条说明 |
| L4 人工介入 | 冲突三选项、备份恢复、重定位 | 不可自动判定 | 对话框 |
| L5 拒绝执行 | 备份校验失败、路径非法 | 高风险 | 明确失败原因 |

**原则**：能在 L1/L2 解决的绝不升到 L4；但**绝不在 L4 的问题上代用户做选择**（EX-03 的三选项即为此原则的体现）。

# 13. 附录

## 13.1 状态机汇总

**索引状态**：`unavailable → rebuilding → ready`；`ready → offline`（网络盘断连）；`ready → rebuilding`（手动/损坏）。

**同步状态**：见 §3.5。

**笔记编辑状态**：`clean → dirty → saving → (clean | conflict_paused | read_only)`；`conflict_paused → clean` 仅在用户作出选择后。
