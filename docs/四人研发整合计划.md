# NoteBase 四人研发整合计划

文档版本 1.0；分析日期 2026-10-31；状态：待团队评审。软件版本不因本次规划修改。

目标是在已有 Tauri 2、Rust、TypeScript 工程上，先整合成员一、二、四的真实业务闭环，再接入成员三的渲染、导出与数据保障，最后统一验收和发布。成员四组织集成，各模块负责人修复本模块问题；我们继续承担成员一，不接管其他成员业务。

## 4 集成顺序和里程碑

从团队确认基线后的 D1 计算。以下是四人可并行投入下的初步工作日估算，不是固定交付日期；成员三完成度核实后重新估时。每个阶段必须通过退出条件才能进入下一阶段发布范围。

| 阶段 | 建议时段 | 工作及负责人 | 退出条件 |
|---|---|---|---|
| M0 基线与契约 | D1–D2 | 四冻结 SHA、需求矩阵与集成分支；一二核对存储/索引接口；三提交当前交付清单 | 来源明确、阻塞有归属；所有接口争议有决定或显式阻塞；main 基线检查有当前结果 |
| M1 一二四整合 | D3–D5 | 四从最新 main 建集成分支，先合成员四；一二处理业务冲突；再合成员一已推送且审阅的性能分支 | 保存→磁盘→队列→检索、迁移后草稿恢复、多窗口冲突、关闭保护同时通过；保留原两侧测试，不以全量重建绕过增量错误 |
| M2 预览和导出 | D6–D8 | 三先交 renderer 与真实导出服务；二接链接解析；四接预览/进度/错误 | Markdown/HTML/PDF 与整库导出按需求抽样验收；附件、中文、歧义和缺失资源有结果与报告；不能用浏览器 mock 作为桌面通过证据 |
| M3 快照和备份恢复 | D9–D12 | 三交保存快照、历史及备份恢复；一接暂停/业务状态/重建；二接保存结果；四接恢复交互 | 备份可脱离应用还原；恢复前快照；恢复后文件/附件/哈希一致且索引收敛；失败不损坏原库，能恢复原会话 |
| M4 系统验收与候选版 | D13–D15 | 四组织；一负责规模性能和索引修复，二负责编辑与链接，三负责导出与恢复 | 需求追溯有证据；阻断缺陷清零；安装/升级/卸载及目标平台按承诺通过；软件版本统一 |
| 缓冲 | D16–D18 | 各负责人解决联调与环境问题 | 未达门槛延后发布，不能用缓冲结束代替验收 |

同步作为独立后置阶段：三先交 WebDAV、冲突副本与系统凭据存储，随后一接文件变化收敛、四接状态重试。若本轮不纳入，需求清单标“延期及批准人”，不得删除需求或将六个缺失服务全部标为完成。成员三若无可接入代码，D6 以后改为重新估算，M1 可单独交付开发集成版本。

## 5 Git 合并与共享文件管理

1. 每轮先读取远端 main 与各分支 SHA、检查工作树；变化后重新评估，不在未提交修改上直接 pull。成员一本地性能分支先单独审查、推送、核实远端，文档分支不夹带性能代码。
2. 建议由四从最新 main 建 `integration/team-core`，合入成员四，解决一二四的功能重叠，再接成员一性能分支。成员二原交付已在 main，不重新 cherry-pick，不整文件覆盖 main.ts/application.rs。
3. 对 `application.rs`、`lib.rs`、`src-tauri/src/main.rs`、`src/main.ts`、contracts/bridge、设置和锁文件，由四维护集成窗口，模块负责人评审本模块语义。保留双方回归与历史证据；重新生成锁文件时解释依赖变化。
4. 成员三按“渲染导出”“快照备份”“同步”分小 PR，依赖前一个已验收提交。每个 PR 更新 CHANGELOG、接口说明和需求状态；测试失败留日志，修复后重跑受影响项与组合链路。
5. 集成分支通过检查后提交 main 的评审与合并；功能分支已推送不能写成 main 已合并。禁止强推、覆盖已有标签；本计划不执行任何业务分支合并或正式发布。

## 6 跨模块验收矩阵

| 场景 | 主要负责人 | 必查结果 |
|---|---|---|
| 新建→连续输入→自动保存→检索→重启 | 二、一、四 | 文件正文与确认 revision 一致；索引最终一致，indexQueued 不冒充完成；确认草稿可恢复 |
| 外改与双窗口编辑 | 二、四、一 | 旧基准不静默覆盖；冲突弹窗关闭保持暂停；迟到回包不污染当前库/编辑状态 |
| 重命名预演、取消、执行中断与续跑 | 二、一 | 取消零写；部分完成有日志且索引追平；链接不误改；重启后可幂等续跑 |
| 删除、恢复、附件与目录级变化 | 二、一、四 | 不覆盖同名文件；过期清理符合规则；附件引用与树/搜索一致 |
| 索引损坏、重建和迁移 | 一、二、四 | 业务表/草稿/恢复日志保留；降级、零结果、不可服务可区分；新库哈希清单一致、源库保留 |
| 共用预览及导出 | 三、二、四 | 同一样例的链接/附件/代码块一致；HTML 安全；PDF 中文和分页正确；失败资源可定位 |
| 保存后快照、备份与恢复 | 三、二、一、四 | 保存与快照结果分别可见；暂停相关后台写入→快照→恢复→校验→重建→恢复服务；失败路径可回退 |
| 设置、多窗口、日志与安装 | 四 | 配置兼容及坏文件保护；快捷键真机触发；日志无正文/路径/凭据；干净环境安装、升级、卸载可复现 |

恢复期间暂停范围应覆盖同步、索引写队列、watcher 处理及编辑写入；究竟拒绝、排队还是取消由契约评审确定。恢复与迁移失败必须释放互斥状态并给出可见错误，不能永久停住服务。

常规检查沿用工程脚本：`cargo test --locked --manifest-path crates/notebase-core/Cargo.toml`、核心 fmt/clippy、`npm test`、`npm run build`、`npm run test:e2e`、`npm run desktop:build -- --no-bundle`、`npm run test:desktop`。在工程目录运行；四的验证脚本接入后核对其覆盖范围。Windows MSVC、WebView2、浏览器或其他平台缺失时登记环境阻塞。

性能沿用已冻结门槛，不用新计划放宽：10 万篇约 500 MB，查询各 100 次，长查询首屏 P95≤50 ms、两字中文 P95≤1 s且集合/计数等于真值；全量重建≤30 min；最终索引≤语料三倍，另列 WAL/临时双库峰值；正常监听变更≤1 s可检索。20 万篇长查询 P95≤100 ms、短查询 P95≤2 s。四牵头整机冷启动≤2 s、常规内存≤1 GB及输入时延验收；轮询、网络盘和跨平台各记独立证据，不套用本地监听成绩。

每份新报告记录提交 SHA、系统硬件、依赖、语料种子、命令、样本、冷/热缓存和原始结果；本地性能分支的预试验与失败日志不作为最终通过证明。
