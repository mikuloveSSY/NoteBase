当前工程处于可继续开发的基础骨架阶段。成员一应先修正文件存储与需求的偏差，再建立索引和检索闭环，最后补齐外部变更、重建、迁移及性能证据。本计划只安排成员一的实现与必要联调，不将其他成员的业务纳入我们的独立交付。

## 1 资料与需求依据

本地只有一个可构建的软件项目：`NoteBase-主干基础工程-v0.1.0/notebase-starter`。其中前端为 TypeScript、Vite、CodeMirror 6，桌面入口为 Tauri 2，核心为独立 Rust crate；它们是同一应用的组成部分，不是多个独立产品。

已核对的资料包括需求分析 v0.3、软件设计 v1.2、需求基线 v1.2、AI 协作记录、人工核实说明、四人任务分工 Word、工程 README、团队开发指南、验证记录及 AI 交接包，并检查核心代码、前端、IPC、测试及配置。工程 reference 中三份主要文档与外层同名文件的 SHA-256 一致。

资料使用顺序：

1. 成员归属以 2026-10-26 的四人任务分工方案为准，该方案明确重新分配旧交接包的工作。
2. 需求内容与验收以需求分析 v0.3、需求基线 v1.2 为准。
3. 实现架构以软件设计 v1.2 为准；与需求不一致之处记录后协调，不静默修改需求。
4. 现有实现状态以源码和实际验证为准，文档中的勾选、历史数据不等于软件已完成。

软件总需求为 82 条：46 条功能需求、18 条非功能需求、10 条时间需求、8 条业务规则。核心是本地优先的 Markdown 笔记工具，文件为权威数据源，索引可重建。功能涵盖编辑、组织、检索、链接、导出、备份、同步和设置；同步保留为后置弹性范围。移动端、多人实时协作、账号云服务、插件系统等不在范围内。

人工核实说明中仍有访谈、实际应用内存、输入延迟、真实网络盘等未完成核实项。实现计划沿用当前基线，但不能把这些需求假设写成已完成的用户验证。

对成员一而言，五个负责组件中只有 fs-store 存在部分实现，index-store、index-worker、watcher、search-svc 尚未落地，因此尚未达到成员一交付标准，也未达到旧 W1 的完成定义。

## 3 我们的职责边界

成员一负责 fs-store、index-store、index-worker、watcher、search-svc，以及路径领域规则、数据库结构和迁移材料。

| 对接对象 | 我们提供 | 对方负责 |
|---|---|---|
| 成员二 | NoteStore、IndexStore、IndexQueue；原子操作、索引读写及异常约定 | 保存判定、自动保存、草稿、冲突交互、删除恢复业务、链接解析及重命名流程 |
| 成员三 | 文件读取、数据库访问端口、恢复期间索引暂停及重建协作 | 共用 renderer、导出、快照、备份、同步和凭据 |
| 成员四 | 库管理、search、index_status、index_rebuild 的服务实现与事件载荷 | UI、IPC 装配、设置入口、状态展示、日志和打包 |

我们统一维护全部既定数据表的结构，但不因此接管备份、同步、链接的业务。链接数据来自成员二的解析规则，索引正文抽取与成员三共用解析方案；不能各自建立不一致的 Markdown 解析器。

成员四应从第一阶段参与 Windows 启动、接口装配和状态展示，而不是最后才开始接入。旧交接包将 watcher 放 W4、search-svc 放 W3 的分法不再用于成员归属。

## 4 首轮必须解决的问题

| 问题 | 现状或冲突 | 处理安排 |
|---|---|---|
| BOM 和非法编码 | application.rs 保留 BOM、拒绝非法 UTF-8；FR-EDT-10 要求写入无 BOM、非法编码只读展示并提示 | 首轮修正，并与成员二协调读取 DTO、保存规则；同步修正现有 BOM 测试预期 |
| 路径和名称 | 缺少归一化、COM¹ 等保留名和既定长度约束；创建时拒绝非法名称，而需求有替换并提示用例 | 提供严格路径校验与名称处理规则，成员二接创建流程、成员四显示提示；禁止自动改写已有磁盘路径 |
| 超大文件 | 超过 10 MB 直接报错，未只读打开 | 明确有界读取或分段预览方案，与成员二、四协商错误信封和只读内容如何同时表达 |
| 原子写与竞态 | 已做临时文件替换；未覆盖 Windows 锁、写满和检查后外部变更竞态 | 故障注入验证；文件锁与业务写入保护分工明确，不能以目前哈希测试宣称消除所有竞态 |
| 全库枚举及全局锁 | 每次列表全量扫描，IPC 核心共享 Mutex | 优先避免索引构建占用全局锁；保留 per-path 保存保护，索引使用单写者和独立读连接 |
| 字段缺口 | hasAttachment 恒为 false；检索请求示例仅含修改时间过滤，需求还含创建时间 | 记录共享 DTO 差异，协商补齐字段后同步 TypeScript、Rust、文档和测试 |
| 设计内部歧义 | 路径 NFKC 与 notes.path 的 NFC 注释并存；FTS 说明又说 notes 存正文又说只存元数据 | 在实现前形成短决策记录；以 SQL 模式为存储核对依据，不擅加正文列；区分校验规范化与磁盘身份 |
| 重建与业务状态 | 索引整体可丢弃，但同库还有同步状态、重命名日志、快照索引 | 与成员二、三核实恢复来源与保留策略，再实现重建/版本切换，避免把不可恢复状态随缓存清空 |
| 降级语义 | 短查询回退、部分结果、不可服务的文字口径存在差异；重建查询有旧索引/部分索引加扫描描述 | 第一阶段统一响应样例；空结果、正常回退、部分结果、不可服务分别测试，不静默返回假空集 |
| 性能证据 | 原 evidence 缺失；历史更新耗时不含完整 watcher 链路 | 新验收测“文件变更到可查询”，保留原始日志、机器配置与提交号 |

以上是需要解决的实现问题与契约议题，不代表已修改冻结接口。对确需变更的命令、事件、错误码、表或共享字段，先记录影响与协商结果。

### 0.1.1 基线整理

- 将现有源码纳入指定仓库的普通目录跟踪，保留原 ZIP 归档；与成员四确定唯一工程入口，避免继续靠 ZIP 交换版本。
- 补齐 Rust MSVC 环境并检查 Windows 桌面依赖，记录版本与构建命令。
- 运行既有测试，保存本机基线；区分 Unix 专属测试与 Windows 测试。
- 优先解决第 4 节共享契约议题，并整理 NoteStore、IndexStore、SearchQuery、SearchPage、IndexStatus 的样例。
- 找回 evidence 或登记缺失并准备可追溯的新基准方案。

### 0.2.0 存储完善

按设计 §5.5.1 补齐 read、write_atomic、create_new、rename、delete、list、stat，使用 RelPath 等共享值对象。delete 的底层能力与“删除即移入回收站”的业务不能混淆，普通删除必须由成员二编排为移动。

覆盖非法路径、上标保留名、中文路径、规范化碰撞、同名创建、CRLF、BOM、非法编码、超限文件、权限拒绝、磁盘写满、文件被占用和临时文件清理。只读降级不得偷偷保存替换字符。需要修改 application.rs 时只做与端口迁移有关的协作改动。

### 0.3.0 索引基础

- 按原设计建立 10 张逻辑表；FTS5 自动生成的影子表不作为手工维护的新业务表。
- note_fts 使用普通 FTS5 trigram 表，自带内容；不得改成 external content 或 unicode61。
- 索引放应用数据目录的 vaults/<vault_id>/ 下，不能放入笔记库或随用户笔记同步。
- 配置 WAL、外键、单写连接和两个只读连接；notes、FTS 及相关元数据按事务保持一致。
- 落实 schema_version、tokenizer_version 检查和重建策略，并保留第 4 节要求协调的业务状态。
- 提供独立于 Tauri 的核心测试或命令行验证入口，先用小库验证，再扩大规模。

### 0.4.0 检索闭环

- 按 Unicode 字符处理查询长度；至少覆盖单字、两字、三字、长词、中英混合和跨词边界子串。
- 长查询走 trigram；短查询先标题/别名/标签，再扫描既定 FTS 内容副本；用真实 schema 核对影子表列名。
- 实现双引号短语、减号排除词，以及 tag:、path:、title:，不能把解析错误偷偷改为普通搜索。
- 标签、目录、创建/修改时间、附件过滤与相关度/修改时间排序均须验收；创建时间字段先完成契约协调。
- 去重、稳定排序和游标分页不得漏项；高亮片段必须转义原始 HTML。
- 对 LIKE 中 %、_、引号及组合查询进行边界测试，避免把用户输入误当通配语法。
- 返回 degraded、degradeReason 等约定字段，区分零结果、部分结果和 E_QUERY_UNSUPPORTED / E_INDEX_UNAVAILABLE。

### 0.5.0 增量与监视

按既有设计实现专用单写者、每批最多 200 篇、有界队列和路径去重。先文件写入成功，再排队更新索引；队列接收与实际更新完成必须区分。

watcher 回调只入队；覆盖原生文件事件、重复/乱序事件、编辑器临时文件替换、删除、重命名、队列溢出。采用默认 300 秒对账及不可监听时轮询降级。正常监听的 1 秒端到端目标与轮询降级的收敛时间分别记录，不能将轮询模式也宣称满足 1 秒。

接入既有 note.changed、index.progress、index.state、error.raised 等适用事件，避免本窗口保存响应与事件重复通知。停止、切库、恢复备份时处理旧队列和后台任务，防止写错库。

### 0.6.0 重建与迁移

手动 index_rebuild 立即返回 jobId，后台构建、报告进度；遵循协调后的旧索引/扫描降级策略。测试无旧索引、损坏索引、版本不匹配、任务中断、重建中持续编辑及完成时切换。

目录迁移先校验目标、文件清单和可用空间，再执行复制/切换；至少比对文件数，并用路径和内容哈希防止“数量相同但内容不同”。失败时保留原目录；清理原数据不作为自动步骤。重新计算 vault_id 并触发索引重建，设置和界面入口由成员四接入。

### 0.7.0 验收交接

先做功能正确性和故障注入，再跑大规模基准。输出可重复执行脚本、固定种子或语料清单、机器和系统配置、依赖版本、运行命令、原始日志、结果 JSON 和代码提交号。报告中区分冷/热缓存、首屏耗时、完整结果计数和端到端时延。

性能硬门槛沿用原设计：

| 指标 | 规模与条件 | 通过标准 |
|---|---|---|
| 长查询首屏 | 10 万篇约 500 MB，各查询重复 100 次 | P95 ≤50 ms |
| 短查询首屏 | 同库，两字中文词各重复 100 次 | P95 ≤1 s，返回集合和计数等于真值 |
| 子串与标记词召回 | 含跨词边界子串、100 个植入标记词 | 按真值全部正确，不能只验证非空 |
| 全量重建 | 10 万篇 | ≤30 min |
| 索引体积 | 同语料，明确 DB/WAL 等统计口径 | ≤语料 3 倍 |
| 增量更新 | 正常本地文件监视模式 | 变更后 1 s 内可查询；单列尾延迟与超时 |
| 大库模式 | 10–20 万篇，20 万篇执行 VT-PER-07 | 长查询 P95 ≤100 ms，短查询 P95 ≤2 s，并展示档位提示 |

整机冷启动 ≤2 s、常规内存 ≤1 GB、三平台兼容由成员四牵头，成员一提供索引相关测量和修复。网络盘需要真实环境测试；只有本地 Windows 通过不能标记三平台或网络盘通过。

## 7 每版的仓库和版本说明规则

唯一目标仓库为 https://github.com/mikuloveSSY/NoteBase 。用户已要求之后所有版本迭代推送至此仓库，并持续维护版本说明。

- 使用源码提交，不以仅上传 ZIP 代替源码版本管理。
- 每次迭代先读取远端最新状态，在成员一功能分支开发并推送；共享 main 的集成遵守团队合并流程，禁止强制覆盖他人提交。
- 每版必须更新根目录 CHANGELOG.md，记录版本、日期、功能变化、修复、关联需求、接口/数据变化、测试结果、未完成项和迁移注意事项。
- 实现代码、契约调整、测试、说明应共同提交；未通过的检查如实登记，不标记可发布。
- 正式软件版本同步 package.json、package-lock.json、两个 Cargo.toml 及相应锁文件、tauri.conf.json 和可见版本展示；纯计划文档修订不虚增软件版本。
- 发布时创建对应版本标签并推送；标签代表通过验收的具体提交，不覆盖已有标签。
- 推送后读取远端提交确认成功，在交付回复中给出分支、提交和版本说明链接。认证或网络失败时说明“本地完成但未推送”，不得声称已同步。
- 代码仓库不提交真实笔记、凭据、node_modules、target、安装缓存、大规模生成语料或 index.db；基准生成器和脱敏结果应提交。
